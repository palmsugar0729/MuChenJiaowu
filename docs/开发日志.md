# 开发日志

## 2026-10-05 — Phase 2W：Web 版起步（脚手架 + 登录闭环）

### 为什么先做 Web 而不是直接上 uniapp

原计划 Phase 2 直接上 uniapp。改主意了：**先用普通 Web 把产品流程验证通，再上 uniapp**。

理由：uniapp 的工具链和坑多，而当前真正不确定的是**「流程顺不顺」，不是「能不能编译成小程序」**。
用普通 Web 验证，成本低得多——而且登录相关的后端接口 Phase 1 已经全部做完，
第一天就能把 **构建 → 代理 → JWT → 强制改密** 整条链路跑通，工具链有问题立刻暴露。

**Web 版定位是「一次性流程原型」**：验证通过后由 uniapp 重做 H5，Web 冻结归档
（跟桌面版 exe 一样的处理思路）。所以分层上刻意把逻辑层和视图层分开，将来只重写视图。

### 完成事项

- `codes/web/` 从零搭起来（此前只有 `.gitignore` 里预留的路径，目录从未建过）
- 登录 → 强制改密 → 首页，完整闭环
- **经 Vite 代理**跑通全链路实测（见下方「验证记录」）
- `npm run build` 通过

### 本轮范围

**只做脚手架 + 登录闭环，不碰课程/考勤。** 那些后端接口还不存在，
要等 Phase 2+3 后端合并做（原因见「一个排期发现」）。

### 技术选型

Vue 3 + Vite + Vue Router + Pinia，**手写 CSS**（不引 UI 组件库，品牌色完全说了算），
**原生 `fetch`**（不引 axios，封装约 60 行），**JavaScript 不用 TypeScript**
（接口契约由后端 Pydantic 保证，读得懂比类型安全重要）。运行依赖只有 3 个。

实测版本比预期新：`vue 3.5.43` / `vue-router 5.3.1` / `pinia 4.0.3` / `vite 8.3.2`。
两个大版本号**都不带破坏性变更**，但各有细节：

- **Vue Router 5** 核心 API 与 v4 完全一致（这个 major 只是把文件式路由并进了核心），
  但 **5.0.3 起弃用了守卫里的 `next()` 回调**，一律用返回值写法
- **Pinia 4** 是纯 ESM，`@vue/devtools-api` 拆成了 peerDependency

### 关键决策

| 决策 | 理由 |
|---|---|
| **前端只写相对的 `/api`，靠代理** | dev 用 Vite 代理转发到本机 8000，生产用 Nginx 反代。**手机访问时不用改后端 CORS**（同源了），一份代码两处跑 |
| **`client.js` 不 `import router`，改用注入的回调** | 否则 `router → store → api → client → router` 循环依赖，还会把 web 独有的路由拖进本该可移植的网络层。改成 client 只认两个回调，在 `main.js` 里接线 |
| **判定「会话失效」= `401 && 本次带了 token`** | ⚠️ 见下方踩坑 1 |
| **token 存 localStorage，user 不持久化** | role 是权限依据，宁可每次启动向后端要一份真实的 |
| **不建 `components/`** | 只有 2 个表单，抽组件是负收益；而且组件越抽象，移植 uniapp 时越要重写 |

### 踩坑记录

1. **⚠️ 登录失败和 token 过期是同一个状态码** —— 后端密码错也回 401
   （不给撞库的人区分「这个号存在」）。如果 client 把「401 → 登出」写成无条件触发，
   **用户输错一次密码就会被踢出登录态**，而且看起来像玄学。判定条件必须是
   「带了 token 还被 401」。这是本轮最容易写错、也最难查的一处
2. **改密接口只回 `{message}`，不回 user** —— 读源码才发现的。前端改完必须
   自己把本地的 `must_change_password` 置回 false，等响应体是等不到的，
   否则路由守卫会一直把你摁在改密页
3. **`init_superadmin.py` 在 Windows 下会「成功了却报错」** —— 最后一行打印
   `⚠️`，GBK 控制台编不出来，抛 `UnicodeEncodeError`。账号**已经建好了**，
   脚本却带着 traceback 退出，看着像失败。已换成纯中文
4. **手机连不上多半是防火墙** —— Vite 默认只绑 localhost，要 `host: true`；
   另外首次启动时弹的「允许 Node.js 访问网络」如果点了取消，之后不再弹窗

### 一个排期发现

**Phase 2 的验收标准依赖 Phase 3 的数据。**
实施计划里 Phase 2 的验收是「提交考勤 → 该课变已完成，**学生课时被扣**」，
但**学生和班级是 Phase 3**。没有班级就没有课，没有学生就没得扣。

所以 **Phase 2 和 Phase 3 的后端必须合并做**，不能按编号顺序走。实施计划已同步修正。

### 一个实测确认的隐患

**设计文档要求的枚举 `CHECK` 约束，实际一条都没建出来。**
SQLAlchemy 2.0 的 `Enum` 默认 `create_constraint=False`，实测 `users.role`、
`lessons.status`、`attendance.status`、`hour_transactions.type` 建出来都是裸 `VARCHAR`。

最要命的是 `hour_transactions.type`：`uq_consume_once` 这个防重复扣课时的部分唯一索引，
条件是 `WHERE type = 'consume'`——**它的正确性完全押在这个字符串字面量上**。
写错大小写索引就静默失效，同一节课扣两次课时。

**建议尽快修**：现在生产库只有超管一个账号，重建表几乎零成本。已记进实施计划待办。

### 验证记录

本地起后端 + Vite，**经 `http://127.0.0.1:5173` 的代理**（不是直连 8000）跑通：

| 用例 | 结果 |
|---|---|
| 密码错 | 401 + 「手机号或密码不正确」（无 token） |
| 登录成功 | 200，`must_change_password: true` |
| 带 token 取 `/users/me` | 200 |

| 合法改密 | 200 + `{message}` |
| 新密码登录 | `must_change_password` 变 false |
| 旧密码登录 | 401 |

### 踩坑记录

1. **测试断言写太粗** —— 用 `"password" not in resp.text` 检查密码没泄露，
   结果被 `must_change_password` 这个字段名误伤。改成对着**真实哈希值**断言，
   比排除关键词准得多
2. **漏算「管理员自己也在列表里」** —— `/admin/users` 返回的是全员名册，
   不是「我能管的人」。测试一开始按后者写的，误报失败

### 一个发现

「不能停用最后一个超管」这条护栏**目前从接口走不到**：停用超管必须由超管本人发起，
而「不能停用自己」已经先一步挡住了，所以请求只要发得出来，场上就至少有一个超管。

护栏**保留**——「绝不能没有超管」是这个系统真正的底线，哪天有人放宽「不能停用自己」，
它必须立刻兜住。但只给它写了服务层测试，没写接口测试（写了也只能是靠绕过接口才通过）。

## 2026-10-04 — ⚠️ 更正：关于「改不了角色」的理由（同日）

### 记错的是什么

上面 Phase 1 的决策表里，「改不了角色」原本写的理由是
**「改角色等于把过去的记录算到另一个身份头上」——这句话是错的。**

改角色时 `user.id` **不变**。梁筱的 200 节课 `teacher_id` 还是梁筱，
工资统计一分不差。**她确实教了那些课，这个事实没有被改写。**

那句话实际描述的是另一件事：**把账号交给另一个人**
（梁筱离职、张三用她的号登录）。那才叫篡改历史，和改角色是两码事。

### 为什么不能再照这个理由做决定

用户当时提出「新建一个管理员号，再把老师的数据复制过去」——
这个绕法**恰恰是在改写历史**：

```sql
UPDATE lessons SET teacher_id = 新号 WHERE teacher_id = 旧号
```

- `created_by` 散在多张表里，漏改一个就是孤儿记录
- 一个人从此有两个账号，不知道登哪个
- 旧号留在库里，哪天被别人拿去用，历史**才真的**错位了

**结论：改角色本身是安全的、正常的。** 要这个能力就直接放开（约 10 行：
只有超管能改、不能改自己），**不要去复制数据**。

### 现状

本期**没做**角色修改，是范围控制——当时只有超管一个账号，用不上。

## 2026-10-04 — 桌面版 v0.4：班级名 → 班级类型 联动

### 背景

班级名其实是一串**编码**（如 `YDY001N5`），开头几位就决定了班级类型，
每次还要手动在下拉框里再选一遍属于重复劳动，且容易选错。

### 新增规则

| 班级名前缀 | 班级类型 | 交互 |
|---|---|---|
| `YDY` | 1对1 | 自动填好，**锁死不可改**（输入框置灰） |
| `YDE` | 1对2 | 同上 |
| `XB` | 小班 | 下拉可选 1对3 / 1对4 / 1对5，**默认 1对3** |
| 认不出 | — | 沿用原状：全部费率类型随便选，也可自己输入 |

- 前缀匹配**不分大小写**，前后的空格忽略
- 「后面有啥别管」——`YDY` 后面跟什么都不影响判定
- 边打字边联动（`currentTextChanged`），双击表格改记录时也按此规则回填
- 已有数据的班级名若不以这三个前缀开头（如「周三班」），行为**和以前完全一样**，不做迁移

### 文件变更

| 文件 | 操作 | 说明 |
|---|---|---|
| `codes/desktop/config.py` | 修改 | +`CLASS_NAME_RULES` / `SMALL_CLASS_*` 常量 + `class_type_rule()` |
| `codes/desktop/ui/main_window.py` | 修改 | +`_apply_class_type_rule()`，`_refresh_class_combo` 改由它驱动 |

### 打包

- 产出 `dist/SalaryCounter-v0.4.exe`（68,491,395 字节），**与 v0.3 及更早的 4 个历史 exe 共存**
- `dist/` 下的 `records.json`、`梁筱_工资结算表.xlsx` 未触碰

### 备注

⚠️ **这条前缀规则是业务规则，后端也要用**——Phase 3 做班级管理时，
班级编码的校验/自动定类型应复用同一套前缀定义，不要在后端另写一份。

### 踩坑记录

1. **仓库改名** —— `salary-counter` → `MuChenJiaowu`，本地 remote 与手册 clone 地址同步更新
2. **`git clone <url> .` 末尾的点看不见** —— 看漏就多套一层目录，后续所有路径全废。手册改为显式绝对路径 + `ls` 验证
3. **SSH 私钥不在 `Downloads`** —— 实际在 `D:\密钥\`，`~/.ssh/config` 里 `jplearning` 那条路径一直是错的，用户一直以为在用密钥登录，其实每次都在敲密码

5. **Git Bash 的 ssh 不检查 Windows ACL** —— 同一份 config，Git Bash 里连得上、cmd 里报错。**验证必须用 `C:\Windows\System32\OpenSSH\ssh.exe`**

| 决策 | 理由 |
|---|---|
| `init_superadmin.py --name` 填**真实姓名** | 它是 `display_name`，会出现在审批记录、操作日志、导出表格里；系统用手机号登录，没有「用户名」概念 |

| 测试用**每测试清表**而非 drop/create | 快得多，且表结构是 session 级的不用重建 |

### 踩坑记录

1. **索引建了两次** —— `Approval.status` 上既写了 `Field(index=True)`，又在 `__table_args__` 里建了同名 `Index("ix_approvals_status")`，`create_all` 直接报 `index already exists`。**两者只能留一个。**
2. **SQLModel 0.0.47 拒绝朴素 datetime** —— 报错要求带时区或标注 `NaiveDatetime`，但**这个类在新版里已经不存在了**（只剩 `UTCDateTime`）。
3. **`UTCDateTime` 不能直接当类型注解** —— 它是 SQLAlchemy 类型，pydantic 会报 `Unable to generate pydantic-core schema`。正确写法：注解仍写 `datetime`，用 `Field(..., sa_type=UTCDateTime)`。
4. **测试之间互相污染** —— 夹具硬编码同一个手机号，第二个测试就撞 `UNIQUE constraint failed: users.phone`。加了 autouse 清表夹具。

### 部署方案二次变更（同日晚）

用户提出：系统将来要**被公司买断**，服务器和后期运维仍由用户自己承担。据此改了部署方案。

| 项 | 原方案 | **新方案** |
|---|---|---|
| 服务器 | 与刷题背单词站共用现有 4核4G | **独立新服务器，2核2G / 40G / 3~5Mbps** |
| 域名 | `jiaowu.palmsugar.cn` 长期沿用 | **开发期沿用，交付期换公司企业备案域名** |

**改的原因**（三条，按硬度排）：
1. **数据隔离** —— 学生表含姓名、性别、是否成年、电话，属**未成年人敏感个人信息**（PIPL），不该与个人项目混跑
2. **故障隔离** —— 个人站挂了不该连带公司的考勤系统下线，反之亦然
3. **责任清晰** —— 买断后这是交付物，跑在独立机器上才说得清

**关键发现——「先用个人名义备案，以后再转公司」是条单行道**：

- 绝大多数省份**不支持个人备案 → 企业备案直接变更**，只能注销重备
- 注销重备期间**网站必须停摆**（域名无法访问境内服务器），审核 1~20 工作日
- **小程序被一起锁死**：小程序备案主体须与注册主体一致，主体变更同样要注销重备
- 「域名归我、备案用公司」也走不通——企业备案要求域名实名就是企业

→ **结论：现在什么都别注册**，开发期复用 `jiaowu.palmsugar.cn`（子域名无需单独备案），谈成后由公司注册 + 企业备案，一步到位。

**待确认**：企业备案通常要求备案主体与服务器账号实名主体一致。服务器在用户名下、备案主体是公司，能否用**授权委托书**通过——**买断谈判前问腾讯云备案客服**。

**✅ 切换成本几乎为零**：服务器全程不换，交付时只改一条 DNS 解析，不涉及数据迁移、不停服。这正是「现在就分开服务器」的最大收益。
