### 1. 「第一次的申请记录消失了」 —— 不是显示框太小，是只取了一条

用户猜是「内容框太小显示不出来」。**不是** —— 库里那条记录一直在，只是
`LessonDetailRead.approval` 走的是 `latest_for_lesson()`（`ORDER BY id DESC LIMIT 1`），
**详情页本来只设计成显示「当下这一条」**。提交过两次之后，前一条（撤回的那条）自然就看不见了。

**修法**（按用户定的形态）：**「我的」页加一个入口 →「我的改期申请」**（`/me/approvals`），
里面只有申请记录、不显示课的详情。为此把 `GET /approvals/my` **加回来**（Phase 5 当时有意删过，
见下面 10-10 那条的「不做」表）。它是**只读**的 —— 撤回仍然在课程详情页做，两处不要都放撤回按钮。

- 后端：`services/approvals.list_by_requester()`（`id desc`）+ `routers/approvals.py` 的 `GET /my`
  —— ★ 静态段 `/my` 必须写在 `/{approval_id}/...` 之前
- 前端：`api/approvals.js` 的 `listMyApprovals()` + 新建 `views/MyApprovalListView.vue`
  （一页 10 条，翻页见下）
- ★ 路由名是 **`me-approval-list`**，不是 `mine-...`：`TabBar.isActive` 是 `startsWith(tab.name.replace(/-list$/, ''))`，
  `mine` 跟 tab 名 `me` 不是前缀关系，会**五个 tab 全灭**
- 管理员（含超管）调 `/approvals/my` 拿到**空列表**而不是 403 —— 他本来就提不了申请
  （`require_role(Role.teacher)`），没必要让前端为两种情况写两套
- **一页 10 条**（用户 2026-10-29 追加的）：分页在**前端切**，后端 `/approvals/my` 照样
  一次返回全部 —— 一个老师一辈子的申请也就几十条，为它加一套 `offset/limit/total` 契约不值得。
  页码放 `route.query.page`（同 `date` / `month` 的先例），渲染前用总页数**夹一次**
  （`?page=99` 手改会显示一张空白页，看着像没数据），`watch([page, totalPages])` 把越界的
  URL 修回来。⚠️ 两个都要盯：只盯 `totalPages` 会漏掉「数据压根没超过 10 条」那种
  （它没变化，`?page=5` 永远挂在地址栏）。翻页用 `replace` 不用 `push` ——
  返回键要直接回「我的」，不在历史里留一串页码

### 2. 「每一个框之间紧挨着」

用户建议「加个 margin-bottom 5」，实际做的是 **`.page__inner > * + * { margin-top: 16px }`**
—— 一份全局的垂直节奏，**每一页**都吃到，而不是逐页逐类地补 `margin-bottom`（漏一个地方就又是一个报错）。
16px 跟已有的 `.section`（20）/ `.toolbar` / `.hint` 是同一个数量级，5px 在手机上肉眼几乎看不出来。
后续 `.card { margin-top: 16px }` 这类 scoped 补丁删掉了三处（`MineView` / `LessonListView` / `LessonMonthView`）。

⚠️ 这条**放在 `base.css` 各类定义之前** —— 同样专一性下后定义的类会覆盖它（`.section` 的 20px 要靠后定义生效）。

### 3. 未来的课不能做考勤（用户 2026-10-29 定的）

`lesson_date > 今天` 的课 `POST /lessons/{id}/complete` → **400**（「还没到上课那天，不能做考勤。
要改时间请用「申请改期」」）。**所有人都不行，含管理员。** 改期申请和 `PATCH` 不受影响
—— 老师提前发现上不了，本来就该走改期。

- 用 **400 不是 409**：课的状态没毛病（确实是 `scheduled`），是「现在不能做这件事」，
  跟「课时不够」同一个档位
- ⚠️ **`POST /attendance`（事后改考勤）不拦** —— 它只作用于已完成的课，加了日期判断会把
  历史数据锁死
- ★ **新增 `app/core/time_rules.py` 的 `today_cn()`**：服务器跑 UTC，`date.today()` 在中国
  00:00~08:00 会算成**昨天**，早上的课就被误判成「未来的课」不让考勤。用固定 `UTC+8`
  （中国没有夏令时，也避开 Windows 上 `zoneinfo` 缺 tzdata 的坑）。**以后所有「今天」都用它**
- 前端 `LessonDetailView`：`isFuture` → 隐藏完成上课入口、隐藏考勤卡、顶部给一句提示

### 4. 「第 11 条（首次登录强制改密）没法测」

不是 bug，是**没有可用的测试账号** —— 现有老师账号和超管都登录过多次，`must_change_password`
早就清了。**新建一个临时老师账号**（管理员在「班级/用户」侧建号）首次登录就会撞上强制改密。
本轮没改这块代码，`ChangePasswordView` 的 `home` 那行是 10-10 修的，已经在跑。

### ★ `approve` 里的第二次 `assert_scheduled`（本轮最要紧的守卫）

审批挂着的这段时间里，这节课可能已经被**完成**（老师上完了）或**取消**。
那时再改它的日期，等于改一节**已经扣过课时、工资表上已有记录**的课。

所以 `services/approvals.approve()` 里 `session.get(Lesson, ...)` 之后**再查一次状态**，
不是 pending 的课就 409。`tests/test_approvals.py::test_通过之前课程被完成会报409`
就是冲着这一行来的。

**反向验证（必做）**：把那行注释掉 → 确认那条测试**转红**（`assert 200 == 409`）、
其余 42 条不变 → 再改回来。绿不等于覆盖，`bug-tracker.md` #8 的教训。

### ★ `target_id` 不是外键 + SQLite 会复用 rowid（复审揪出来的真问题）

`Approval.target_id` 是**裸 `int`**（`models.py:274`），不是声明外键。而 SQLite 的
`INTEGER PRIMARY KEY`（rowid 别名，DDL 里没有 `AUTOINCREMENT`）会在**删掉 id 最大的
那行之后复用那个 id**。于是：删掉一节带 pending 申请的课 → 那条悬空审批 → 下一节新建的
课正好捡到同一个 id → **管理员在待办里对着一节毫不相干的课点「通过」，把它的时间改掉。**

`delete_lesson` 里**本来就在删考勤**（同一类隐患、同一个修法），照抄一行即可：

```python
session.execute(sa_delete(Approval).where(Approval.target_id == lesson.id))
session.execute(sa_delete(Attendance).where(Attendance.lesson_id == lesson.id))
session.delete(lesson)
```

> ⚠️ **完成 / 取消课程刻意不清审批行** —— 用户要的正是「课后被完成了再点通过 → 409」
> 那条守卫，那行必须在。管理员靠**驳回**把它清掉。两条测试分别锁住这两种相反的行为。

### 读模型

`services/approvals.py` 用**一条 JOIN** 出班级名 / 老师名 / 申请人 / 审批人四个名字
（`outerjoin` + 3 个 `aliased(User)`），列表页二十来行不会变成八十次查询。
`select_from(Approval)` 是显式点出来的 —— `select()` 的列来自四张表，不写它 SQLAlchemy
猜不出从哪儿往外 JOIN。

两个排序决定：

- `latest_for_lesson` 按 **`id desc`** 取最近一条（id 单调，同秒提交的两条也定得出胜负）
  —— ⚠️ 别「顺手修正」成 `requested_at`
- 待办列表按 **`id` 升序**（先提的排前面）：那是份**待办**，老申请不该被新申请压到屏幕外

`payload` 存 JSON 文本（`ensure_ascii=False`，中文原因在 `sqlite3` 里直接看得懂），
**只由本模块写、只由本模块读**（`dump_reschedule` / `parse_reschedule`）。
解析失败 → **500 不吞** —— 吞掉会让管理员对着一份「空的」申请点通过，课改了却看不出改了什么。

### ★ 前端：那个名字是故意起成 `lesson-approval-list` 的

`TabBar.isActive`（`TabBar.vue:47`）是**剥掉 `-list` 后按前缀**点亮 tab 的。
名字以 `lesson` 开头才点亮「课程」tab；叫 `approval-list` 会**五个 tab 全灭**，
用户看着就像页面坏了。已用 `node` 实测：

| 路由名 | 点亮 |
|---|---|
| `lesson-approval-list` | 课程 ✓ |
| `approval-list` | **（全灭）** ✗ |

路径挂 `/lessons/approvals` 跟 `/lessons/new` 同一个惯例（静态段比 `:id` 优先，不靠顺序兜）。

**守卫顺手改成 `meta.adminOnly`**：原来是硬编码的 `to.name === 'contract-list'`，
每加一个管理员页面就得回来改一次，漏了就是个**静默的权限漏洞**。现在跟 `meta.public`
一路，加在路由定义上，`contract-list` 也补了这个标记。

**横幅要日视图 + 月视图各放一条**（同一个「课程」页的两种视图，只放一边等于切过去就
看不见待办了），样式是 `base.css` 里共用的 `.banner`。⚠️ 角标放 **`onMounted`、不进
`load()`** —— `load()` 是日期/月份驱动的，审批数跟看哪天毫无关系，塞进去就变成翻一天
拉一次审批；拉失败**吞掉**，角标坏了不该把整个课程页拖下水。

### 顺手修的三个小 bug（独立于本轮功能）

1. ★ **改完密码弹一屏红字、人卡在页面上**（`ChangePasswordView.vue:38`）——
   `router.replace({ name: 'home' })`，而 `home` 这个路由随「我的」页上线**被删了**、
   这行没跟着改。已用 `node` 实测：vue-router 5 对不存在的具名路由**是抛异常**

### ★ 最要紧的一条：`date` 是唯一真相源

### ★ 关键决策

**1. 先查明细行，汇总在 Python 里现加 —— 不写 `GROUP BY`**

文档从 Phase 2 起就反复强调「计薪口径要和导出一起做，分开写必然两边对不上」。
兑现这句话的办法不是「写两份然后小心对齐」，而是**结构上只留一条路**：

```python
rows = payroll_service.month_rows(session, month=month, teacher_id=...)   # 一条查询
total_hours, total_salary = payroll_service.totals(rows)                   # 现加
```

`/attendance/my`、`/attendance/summary`、`/attendance/export` 三处**全部消费这同一批行**。
不写 SQL 聚合是为了避开第二种口径（SQL 先乘再舍 vs Python 逐行舍再加）。

⚠️ 顺带定死一个细节：**`round(sum(hours * rate), 2)`，不是 `sum(round(hours * rate, 2))`**。
因为 Excel 里合计那格是 `=SUM(F4:Fn)`，而 F 是**未舍入**的 `=D*E` —— 先乘、求和、最后才舍入，
屏幕上的数字才跟下载下来的表里那一格对得上。差别只在极端浮点下的一分钱，但**能对上**比「差不多」值得。

**2. 导出的验收标准从「逐字节一致」改成「逐单元格一致」**

原文档两处都写着「逐字节一致」。实现时发现这是**做不到也没必要**的：
openpyxl 每次 `save()` 都往 `docProps/core.xml` 写当前时间戳，同一个工作簿存两次字节都不同。
而文档里真正写的验收方法一直是对的 ——「拿同一个月的真实数据，桌面版导一份、服务端导一份，
**逐单元格比对**」。已把标题和措辞统一成「逐单元格」。

**顺手把这条验收自动化了**：`tests/test_export.py` 用 `importlib` 直接加载
`codes/desktop/excel_exporter.py`（那份源码**是被 git 跟踪的**，只有 `dist/` 被忽略，
所以 CI 里也能跑），同一批数据两边各导一份，把值 / 公式 / 底色 / 字体 / 对齐 / 四边框 / 合并区 / 列宽
摊成纯数据后 `==`。另外拿 `dist/records.json` 那份**真实生产数据**再对一遍（缺文件则 skip）。
`docs/实施计划.md` 里那条「手动比对」的硬性验收标准，从此有了自动化的载体。

⚠️ 桌面版是**平铺模块**（`excel_exporter.py` 里写 `from config import ...`），不是包，
得先把 `config` / `models` 按名字塞进 `sys.modules` 再执行它，用完恢复原状。

**3. 费率对拍时**两边**有意不同**，这不算 bug

桌面版 `Record.rate` 查的是 `config.CLASS_RATES` 静态表（导出时现查），
服务端用的是 `lessons.rate`（排课时的快照）—— 快照才是对的（改一次费率不该篡改历史工资表）。
所以对拍时**服务端这一侧也按静态表填 rate**，模拟「排课后没再改过费率」的月份。
拿改过费率的月份比对必然对不上。

**4. `month` 必填，不做「省略 = 当月」**

服务器时区若是 UTC，在月初 00:00~08:00 把「这个月」算成上个月 —— 跟前端不能用
`toISOString()` 取今天是同一个坑。月份一律由前端按本地时间算好传进来。
前端对应加了 `utils/date.js` 的 `monthOf()` / `shiftMonths()`。

**5. 停用的老师照样能查、能导**

离职老师那几个月的工资是**欠着人家的**。所以 `/summary` 和 `/export` 都**不过滤 `is_active`**，
查人时按 id 查、查不到 404 —— ⚠️ **不能**复用 `get_active_teacher_or_400`（那个要求启用状态）。
两条测试专门锁这个（`test_停用的老师仍然出现在汇总里` / `test_停用的老师仍然导得出来`）。

**6. Excel sheet 名的坑**

多人导出是「一个 xlsx，每位老师一个 sheet」（方案 A）。sheet 名 = 教师姓名，
而 Excel 对此有硬约束：≤31 字符、不许含 `: \ / ? * [ ]`、非空、工作簿内唯一，撞上 openpyxl
**直接抛异常**。所以写了 `_sheet_title()`：换非法字符、截长、重名补 `(2)`。
⚠️ **重名只加后缀，绝不合并** —— 合并会把两个人的工资算进同一张表，那是少发一个人的钱。
「一年一度的交报表不能因为某个老师名字里带个 `[` 就 500」，这条值 10 行代码。

另外**本月零课的老师不建 sheet**（一张只有标题和表头的空表是噪音，对应桌面版「无记录不写合计行」）；
**单人导出仍是固定表名「工资结算表」**，跟桌面版一致。

**7. `utils/download.js` —— 第二个平台适配器**

前端原来 `client.js` 固定 `Accept: application/json` + `response.text()`，全前端没有任何
blob 处理。补 `requestBlob()` 时守住一条：**失败仍按 JSON 解析错误体**。
后端出错回的是 `{"detail": "本月没有已完成的课程，无法导出"}`，不能因为这次要的是二进制
就把人话丢掉，否则页面上只剩一个光秃秃的「请求失败（400）」。

落盘是 `<a download>` + `URL.createObjectURL`，这**必然碰 `document`**。
所以新开了 `utils/download.js`，并**把 `AGENTS.md` 里那条规则改准**：原来是
「`api/`、`stores/`、`utils/` 里不许出现 `document`/`window`/`localStorage`」，
而 `utils/storage.js` 本来就是那个例外。规矩的本意是**网络层和状态层必须可移植，
平台差异锁进 `utils/` 的适配器** —— 现在适配器有两个：`storage.js`（存储）+ `download.js`（下载）。
照原文写会让新文件看起来在违规，或者逼人把 DOM 操作塞进页面里，两种都更糟。

⚠️ `revokeObjectURL` 用 `setTimeout` 延后 1 秒：立刻 revoke 的话 Safari 会拿不到文件，
而不 revoke 会把整份 xlsx 钉在内存里。

### ★ 关键决策

**1. 1对2 归进「只有出勤才扣」**

用户的原话：

> 对于 1对1 和 1对2 的学生来说，他买多少课时就是多少，所以就是直接按照学生
> 自己的课时来扣就好，上课了就扣课时，没上就不扣。而小班学生的课时是固定的，
> 一个班里的 3-5 个学生，上课都是同步的，上一次课就消一次的课时。除非没有上课，
> 否则其中 1 个学生没有来也不影响扣课时。我的意思就是没有来的也会扣课时。

**他的分界线不是「人数」而是「课时归谁」**：1对1 / 1对2 的课时是**学生自己买的**，
小班的课时是**整班一起走的**。所以我们把判定集抽成了一个有名字的常量，
不再散着写 `'1对1'`：


并用「把常量改回只有 1对1」验证过它们**确实会红**。

**2. 「班级只记上了多少课时」—— 这个提案不用改代码**

用户问的是要不要「取消班级层面的扣课时数据」。查了一遍：**现在就没有**。

- 扣课时只写 `hour_transactions`，每行都挂着一个 `student_id`，**天然是按学生的**
- 班级那边的 `total_hours` 是 `SUM(lessons.hours) WHERE status='completed'`，
  **每次现算**，是个只读的展示值 —— 它不参与任何扣减，删掉它也不影响一分钱
- 所以「两本账」的风险从一开始就不存在，不需要做数据迁移

- `key` 和 `label` **故意分开**：`key` 进 URL query，所以必须是 ASCII
  （中文进 query 会变成 `%E5%AF%B9%E4%B8%80` 那种没法看的链接）
- **筛的是 `class_type`，不是班级名前缀**。历史遗留的自定义班名（「沐晨提高班」）
  没有 `YDY` 前缀，按前缀筛会让它们切到「1对1」后凭空消失
- 小班三档（1对3/1对4/1对5）**合成一张卡** —— 对用户来说「小班」就是一档

卡的定义从 `CLASS_NAME_RULES` 推出来（`CLASS_TABS`），以后加个前缀会自动多一张卡，
不用改前端。

> ⚠️ **已知口子**：`class_type` 认不出来的班（`VIP` / 冲刺班型）只出现在「总览」里，
> 没有「其他」这张卡。用户没要求，**没有自作主张加**。

### ★ 关键决策

**1. 容量口径不是「1对N → N 人」**

最直觉的写法是 `cap = int(class_type[2])`，得到 1对3 → 3、1对4 → 4。
**错**。用户明确的口径是：

> 1对1，上限 1 人 / 1对2，上限 2 人 / 小班，上限 5 人，**只要没有满 5 人都可以**。

即小班三档（1对3 / 1对4 / 1对5）**共用 5 人上限**，不按档位细分。所以
`CLASS_CAPACITY` 是一张手写的表，不是能算出来的东西 —— 代码里专门写了注释挡住
后来的「优化」。认不出的类型给 `None` = **不限制**，免得把历史自定义类型拦死。

**2. 占名额的人数不能只数「还没有行」的**

第一版 `adding` 写的是「在 `class_students` 里没有行的学生数」。**漏了退班又要回来的**：
退班的行会被清掉 `left_on`，人照样回到在册名单，**他也要占名额**。判据得是
`row is None or row.left_on is not None`。这是写的时候自己发现的，补了一条测试钉住。

**3. 超员的历史数据不写迁移脚本**

dev 库里的 `YDY001N5`（1对1）**真的有 2 个在册学生** —— 规则上线前建的，规则不能追溯。
选择**不动数据库**：`PATCH` 只在类型**真的变了**时才查容量（本来就超员的班改个错别字
不该被拦，否则用户没法自救），入班时拦住，界面上打「超员」标记让用户自己移出。

**4. 分类卡的前缀从后端推导，不在页面里写死**

`stores/meta.js` 的 `classPrefixes` 从 `GET /classes/rules` 的 `class_name_rules` +
`small_prefix` 拼出来。以后后端加个 `YDF`，前端**自动多一张卡**。过滤纯前端做了 ——
班级总数几十个，犯不上多跑一趟接口。

### ★ 那个「一直加载中」的 bug（值得单独记）

`StudentDetailView` 读 `detail.transactions`，但这个字段当时**只挂在
`/students/{id}/hours` 上，没进 `/students/{id}` 的详情**。

于是渲染时 `!detail.transactions.length` 抛 TypeError →
**Vue 丢掉整次更新，DOM 冻死在上一帧**（还停在 `loading = true` 的「加载中…」）→
**接口返回 200，后端日志里什么都没有**。

排查顺序很反直觉：看起来像网络卡住，实际网络 5ms 就回来了（直连 8000 和走 5173
代理都试过），**只有浏览器控制台能看见**。最后是靠截图反推的 —— 标题渲染成
「学生」（`detail?.name || '学生'` 的兜底）、没有「编辑」按钮（`v-if="auth.isAdmin && detail"`），
这两个特征只有 `detail === null` 时才同时成立。

**教训两条**：
- 页面读的每个字段都要对得上后端 schema。改后端字段时先看谁在消费
- 「一直加载中」≠ 卡住。先看控制台

顺手修了同一页面上一句已经过期的话：「考勤功能还没上线，这三个数暂时都是 0」——
考勤上一轮就上线了。

**可选加固（尚未做）**：加一个全局 `app.config.errorHandler`，把这类渲染异常
打到界面上。一个 bug 冻了整页且毫无提示，值得有个兜底。等用户点头再加。

## 2026-10-05 — Phase 2 验收完成：lessons / attendance（后端 + Web 课程视图与考勤页）

### 本轮做了什么

补上 `lessons` / `attendance` 两张表的全部接口，外加 Web 的三个页面
（课程日视图、课程详情 + 考勤、排课表单）。

这是**「能替代桌面版」的最后一块功能**：老师看完今天自己的课 → 勾谁出勤谁请假 →
点一次提交 → 学生课时被扣。上一轮里恒为 0 的两个统计字段
（班级的「累计已上课时」、学生详情的出勤统计）**这轮自动有值了，前端一行没改** ——
当初把形状先定死的判断是对的。

224 个测试全绿（上轮 168 + 本轮 56）。

### ★ 四个关键决策

**1. 考勤与「完成上课」合并成一个动作**

实施计划原文把「完成」和「提交考勤」并列成两个平级接口，但 §Phase 2 的验收标准
写的是「提交考勤 → 该课变已完成，学生课时被扣」——**自相矛盾**。

改成 `POST /lessons/{id}/complete` 收可选的 `items`，一个事务里写考勤 + 扣课时 + 改状态，
**以合并为准**。理由：老师的真实动作就是「勾完点提交」，分两步意味着中间那个状态
（课已扣课时但还没点名）既没用又要额外处理。`items` 保持可省（不带 body 默认全出勤），
跟原签名兼容。

`POST /lessons/{id}/attendance` 保留了，但**只管事后改**，且只允许 `completed` 的课。

**2. `BEGIN IMMEDIATE` 刻意不写**

实施计划 §4.1 原本要求手动 `BEGIN IMMEDIATE` 防并发双扣。**做不到**：
`session.get()` 一执行，SQLAlchemy 2.0 的 autobegin 已经开了事务，
此时再 `BEGIN IMMEDIATE` 直接报 `cannot start a transaction within a transaction`。

而它想防的那件事**已经被数据库层兜住了**：第二个并发事务的 `consume` insert 撞
`uq_consume_once` 唯一索引 → `IntegrityError` → rollback（考勤一起回滚）→ 翻译成 409。

所以真正要写的代码是**在 router 里 `except IntegrityError`**，不是手动控事务。
这也印证了「service 层不 commit」这个约定的价值 —— 事务边界留在 router，
一个 try/except 就能兜住整个多步操作。

**3. 课程生命周期冲突统一 409**

完成 / 取消 / 删除 / 改考勤的状态不对，全部 **409 Conflict**。⚠️
**跟班级、学生模块用 400 表示「已经是停用状态」不一样** —— 那两个是「操作重复了」，
课程这几个是「对象状态不允许这个操作」，语义不同。照抄会得到不一致的接口。

**4. `PATCH` / `DELETE` 只允许 `scheduled` 的课**

已完成的课改 `hours` 会让 `lessons.hours` 跟已经写下的 `consume` 流水（`-旧 hours`）对不上，
工资表当场失真。要改就**取消重排**（取消会把课时退回去，重排再扣一次，账是平的）。

同理 `PATCH` **不允许改 `class_id`** —— 换班就是取消重排，避免「改了班，`rate` 快照算谁的」。

### 其他取舍

- **老师权限边界**：排课限管理员；**完成 / 考勤 / 查看只能操作自己的课**
  （`lesson.teacher_id == self`，否则 403）。老师调 `GET /lessons?teacher_id=` **传什么都无效**，
  服务端强制改回自己的 id —— 否则老师能翻遍全校的课
- **取消课程要退回课时**：删掉该课的 `consume` 流水，学生余额自然回升。但 `attendance` 行
  **刻意保留** —— 那是「本来安排了、后来取消了」的痕迹，删了就看不出原本要给谁上
- **`rate` 服务端快照，接口不收这个字段**：让客户端传费率等于谁都能给自己开 999 元/时。
  `LessonCreate` / `LessonUpdate` 里**根本没有 `rate`**，前端也没有费率输入框
- **没有 `stores/lessons.js`**（偏离原计划）：代码库的真实模式是只有跨页面共享的状态才建 store
  （就 `auth` / `meta` 两个），课程页面各拉各的，store 只是个多余的中转层
- **日视图的日期放 `route.query.date`**：不是组件 `ref`。这样「进详情→返回」不丢日期、
  刷新还在当天、链接能直接发人。用 `watch(date, load)` 而不是在每个入口手动调，
  因为**浏览器前进/后退也会改 query**
- **月视图日历本轮没做**：纯 CSS Grid + 原生 Date 手画是块独立的大工作量，
  日视图已经能验证「老师手机上完成一节课」这条主流程

### ★ 踩到的坑：pydantic 注解被字段名遮住

```python
class LessonUpdate(SQLModel):
    date: date | None = None      # ← TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'
```

报错点在**类创建时**，不是实例化时。原因是 pydantic 求值注解时**能看见类命名空间**：
字段名 `date` 的默认值 `None` 把 `date` 这个类型名绑定掉了，于是 `date | None`
被算成 `None | None`。

`LessonCreate.date: date`（无默认值）能跑，因为那个名字从来没被绑定过 —— 所以这个坑
**只在给字段加默认值的那一刻出现**，看起来毫无道理。

**解法**：`from datetime import date as Date`，用 `Date` / `Date | None`。
顺手把模块里三处原有的裸 `date` 注解也改了，保持一致。

### 顺手修掉一个既有缺陷：枚举 CHECK 约束一条都没落库

上一轮记进待办的那个问题，本轮修了。**修法是删库重建** —— SQLite 不能
`ALTER TABLE ADD CONSTRAINT`，而 `init_db()` 只做 `create_all`，已存在的表不会被改。

具体做法是在 `models.py` 加了个 `enum_check(column, enum_cls, name=...)` 助手，
**从 Python 枚举类推导出 IN 列表**，把约束和枚举钉死在一起。两点值得记：

- **用 `.name` 而不是 `.value`**：SQLAlchemy 的 `Enum` 落库写的是成员**名**。
  本项目各枚举恰好 `name == value`，看着等价，但 `.name` 才是对数据库真正成立的推导
- **改 `__table_args__` 时逐个保留原索引**，尤其 `uq_consume_once` ——
  漏掉它等于拆掉防重复扣课时的安全网，而且不会有任何报错。
  `tests/test_enum_checks.py` 里专门有一条把索引的 `WHERE` 字面量和
  `TxnType.consume.name` 绑在一起的回归测试：改枚举成员名而不同步索引，那里会红

⚠️ **教训**：往枚举里加成员后，测试库每次 `drop_all`/`create_all` 所以会绿，
**生产库不会** —— 必须重建生产库，否则新值被 CHECK 挡在门外。

### 八个正确性要点（这些是取舍，不是实现细节）

1. **重新入班必须复用原行**。`ix_cs_pair` 是 `(class_id, student_id)` **全表唯一**，
   退班再入班直接 `INSERT` 会撞唯一索引。正确做法是清掉 `left_on` 并改 `joined_on`。
   这是本轮最容易写错的一处
2. **`GET /students` 防行数放大**。余额先 `GROUP BY` 聚合成子查询再 LEFT JOIN；
   按班级过滤走 `Student.id.in_(子查询)`，**不再 JOIN 一张表** ——
   多一个 JOIN 会让行数相乘，把 `SUM` 放大成错的钱数（学生在 2 个班，10 课时会显示 20）。
   `coalesce` 保证**没有任何流水的学生也显示 0**，而不是整个从列表里消失
3. **班级 DELETE 是真删，学生 DELETE 是软删**。这两个语义不一样（实施计划 §5.3/§5.4），
   真删前要先清 `class_students`，否则撞外键（`db.py` 开了 `foreign_keys=ON`）
4. **本轮绝不产生 `consume` 流水**。手工入口**显式拒绝**：手工流水的 `lesson_id` 是
   `None`，`uq_consume_once` 根本不拦，放进来那道安全网就形同虚设
5. **批量操作全有或全无**。部分成功会让用户不知道该不该重试，而**重试会重复充值**。
   钱的事，宁可全失败
6. **余额允许为负**。`adjust` 就是用来纠错/退费的，负余额是合法账实，只记录不拦截
7. **费率缺省按类型自动填，但绝不静默兜底**。类型不在费率表里又没给 `rate` → 400，
   否则会录进一个错价，**要等发工资才发现**。PATCH 时改类型**不自动改价**
8. **前缀规则在 `core/class_rules.py` 里是「复制」不是 import**。部署时只上传
   `codes/server`，服务器上没有 `codes/desktop`。⚠️ 两边逻辑必须一致，
   判定不一致会让同一节课在桌面版和后端算出不同时薪

### 踩坑记录

1. **`sqlalchemy.select` 和 `sqlmodel.select` 不是一回事**。单列查询用前者返回的是
   `Row` 元组，`(12.0,) == 12` 会失败；`sqlmodel.select` 才会折成标量。
   抄测试助手函数时漏了这行 import，7 个测试红得莫名其妙
2. **取「今天」不能用 `new Date().toISOString().slice(0, 10)`** —— 那是 **UTC** 日期，

4. **`ClassDetailRead` 加了 `has_lessons`**：原计划让前端「编辑时给个费率提示」，
   但接口不暴露「排没排过课」这件事就没法做。加了之后顺带解决了另一个问题 ——

## 2026-10-05 — Phase 2W：Web 版起步（脚手架 + 登录闭环）

### 为什么先做 Web 而不是直接上 uniapp

原计划 Phase 2 直接上 uniapp。改主意了：**先用普通 Web 把产品流程验证通，再上 uniapp**。

理由：uniapp 的工具链和坑多，而当前真正不确定的是**「流程顺不顺」，不是「能不能编译成小程序」**。
用普通 Web 验证，成本低得多——而且登录相关的后端接口 Phase 1 已经全部做完，
第一天就能把 **构建 → 代理 → JWT → 强制改密** 整条链路跑通，工具链有问题立刻暴露。

**Web 版定位是「一次性流程原型」**：验证通过后由 uniapp 重做 H5，Web 冻结归档
（跟桌面版 exe 一样的处理思路）。所以分层上刻意把逻辑层和视图层分开，将来只重写视图。

### 完成事项

- `codes/web/` 从零搭起来（此前只有 `.gitignore` 里预留的路径，目录从未建过）
- 登录 → 强制改密 → 首页，完整闭环
- **经 Vite 代理**跑通全链路实测（见下方「验证记录」）
- `npm run build` 通过

### 本轮范围

**只做脚手架 + 登录闭环，不碰课程/考勤。** 那些后端接口还不存在，
要等 Phase 2+3 后端合并做（原因见「一个排期发现」）。

### 技术选型

Vue 3 + Vite + Vue Router + Pinia，**手写 CSS**（不引 UI 组件库，品牌色完全说了算），
**原生 `fetch`**（不引 axios，封装约 60 行），**JavaScript 不用 TypeScript**
（接口契约由后端 Pydantic 保证，读得懂比类型安全重要）。运行依赖只有 3 个。

实测版本比预期新：`vue 3.5.43` / `vue-router 5.3.1` / `pinia 4.0.3` / `vite 8.3.2`。
两个大版本号**都不带破坏性变更**，但各有细节：

- **Vue Router 5** 核心 API 与 v4 完全一致（这个 major 只是把文件式路由并进了核心），
  但 **5.0.3 起弃用了守卫里的 `next()` 回调**，一律用返回值写法
- **Pinia 4** 是纯 ESM，`@vue/devtools-api` 拆成了 peerDependency

### 关键决策

| 决策 | 理由 |
|---|---|
| **前端只写相对的 `/api`，靠代理** | dev 用 Vite 代理转发到本机 8000，生产用 Nginx 反代。**手机访问时不用改后端 CORS**（同源了），一份代码两处跑 |
| **`client.js` 不 `import router`，改用注入的回调** | 否则 `router → store → api → client → router` 循环依赖，还会把 web 独有的路由拖进本该可移植的网络层。改成 client 只认两个回调，在 `main.js` 里接线 |
| **判定「会话失效」= `401 && 本次带了 token`** | ⚠️ 见下方踩坑 1 |
| **token 存 localStorage，user 不持久化** | role 是权限依据，宁可每次启动向后端要一份真实的 |
| **不建 `components/`** | 只有 2 个表单，抽组件是负收益；而且组件越抽象，移植 uniapp 时越要重写 |

### 踩坑记录

1. **⚠️ 登录失败和 token 过期是同一个状态码** —— 后端密码错也回 401
   （不给撞库的人区分「这个号存在」）。如果 client 把「401 → 登出」写成无条件触发，
   **用户输错一次密码就会被踢出登录态**，而且看起来像玄学。判定条件必须是
   「带了 token 还被 401」。这是本轮最容易写错、也最难查的一处
2. **改密接口只回 `{message}`，不回 user** —— 读源码才发现的。前端改完必须
   自己把本地的 `must_change_password` 置回 false，等响应体是等不到的，
   否则路由守卫会一直把你摁在改密页
3. **`init_superadmin.py` 在 Windows 下会「成功了却报错」** —— 最后一行打印
   `⚠️`，GBK 控制台编不出来，抛 `UnicodeEncodeError`。账号**已经建好了**，
   脚本却带着 traceback 退出，看着像失败。已换成纯中文
4. **手机连不上多半是防火墙** —— Vite 默认只绑 localhost，要 `host: true`；
   另外首次启动时弹的「允许 Node.js 访问网络」如果点了取消，之后不再弹窗

### 一个排期发现

**Phase 2 的验收标准依赖 Phase 3 的数据。**
实施计划里 Phase 2 的验收是「提交考勤 → 该课变已完成，**学生课时被扣**」，
但**学生和班级是 Phase 3**。没有班级就没有课，没有学生就没得扣。

所以 **Phase 2 和 Phase 3 的后端必须合并做**，不能按编号顺序走。实施计划已同步修正。

### 一个实测确认的隐患

**设计文档要求的枚举 `CHECK` 约束，实际一条都没建出来。**
SQLAlchemy 2.0 的 `Enum` 默认 `create_constraint=False`，实测 `users.role`、
`lessons.status`、`attendance.status`、`hour_transactions.type` 建出来都是裸 `VARCHAR`。

最要命的是 `hour_transactions.type`：`uq_consume_once` 这个防重复扣课时的部分唯一索引，
条件是 `WHERE type = 'consume'`——**它的正确性完全押在这个字符串字面量上**。
写错大小写索引就静默失效，同一节课扣两次课时。

**建议尽快修**：现在生产库只有超管一个账号，重建表几乎零成本。已记进实施计划待办。

### 验证记录

本地起后端 + Vite，**经 `http://127.0.0.1:5173` 的代理**（不是直连 8000）跑通：

| 用例 | 结果 |
|---|---|
| 密码错 | 401 + 「手机号或密码不正确」（无 token） |
| 登录成功 | 200，`must_change_password: true` |
| 带 token 取 `/users/me` | 200 |
| 坏 token 取 `/users/me` | 401 +「登录已过期或凭证无效」（**带 token，前端据此登出**） |
| 新密码太短 / 新旧相同 / 原密码错 | 400 + 对应中文文案 |
| 合法改密 | 200 + `{message}` |
| 新密码登录 | `must_change_password` 变 false |
| 旧密码登录 | 401 |

## 2026-10-04 — ⚠️ 更正：关于「改不了角色」的理由（同日）

### 记错的是什么

上面 Phase 1 的决策表里，「改不了角色」原本写的理由是
**「改角色等于把过去的记录算到另一个身份头上」——这句话是错的。**

改角色时 `user.id` **不变**。梁筱的 200 节课 `teacher_id` 还是梁筱，
工资统计一分不差。**她确实教了那些课，这个事实没有被改写。**

那句话实际描述的是另一件事：**把账号交给另一个人**
（梁筱离职、张三用她的号登录）。那才叫篡改历史，和改角色是两码事。

### 为什么不能再照这个理由做决定

用户当时提出「新建一个管理员号，再把老师的数据复制过去」——
这个绕法**恰恰是在改写历史**：

```sql
UPDATE lessons SET teacher_id = 新号 WHERE teacher_id = 旧号
```

- `created_by` 散在多张表里，漏改一个就是孤儿记录
- 一个人从此有两个账号，不知道登哪个
- 旧号留在库里，哪天被别人拿去用，历史**才真的**错位了

**结论：改角色本身是安全的、正常的。** 要这个能力就直接放开（约 10 行：
只有超管能改、不能改自己），**不要去复制数据**。

### 现状

本期**没做**角色修改，是范围控制——当时只有超管一个账号，用不上。

| 费率不单独建 `rates` 表，合并进 `classes` | 费率就是班级的属性，没有跨班级复用场景，单独建表只多一次 JOIN |
| 审计时间戳**存 UTC**（`sa_type=UTCDateTime`） | SQLModel 0.0.47 只支持这一种带时区的存法。绕过它要 hack 类型系统，不值得 |
| 测试用**每测试清表**而非 drop/create | 快得多，且表结构是 session 级的不用重建 |

### 踩坑记录

1. **索引建了两次** —— `Approval.status` 上既写了 `Field(index=True)`，又在 `__table_args__` 里建了同名 `Index("ix_approvals_status")`，`create_all` 直接报 `index already exists`。**两者只能留一个。**
2. **SQLModel 0.0.47 拒绝朴素 datetime** —— 报错要求带时区或标注 `NaiveDatetime`，但**这个类在新版里已经不存在了**（只剩 `UTCDateTime`）。
3. **`UTCDateTime` 不能直接当类型注解** —— 它是 SQLAlchemy 类型，pydantic 会报 `Unable to generate pydantic-core schema`。正确写法：注解仍写 `datetime`，用 `Field(..., sa_type=UTCDateTime)`。
4. **测试之间互相污染** —— 夹具硬编码同一个手机号，第二个测试就撞 `UNIQUE constraint failed: users.phone`。加了 autouse 清表夹具。

### 部署方案二次变更（同日晚）

用户提出：系统将来要**被公司买断**，服务器和后期运维仍由用户自己承担。据此改了部署方案。

| 项 | 原方案 | **新方案** |
|---|---|---|
| 服务器 | 与刷题背单词站共用现有 4核4G | **独立新服务器，2核2G / 40G / 3~5Mbps** |
| 域名 | `jiaowu.palmsugar.cn` 长期沿用 | **开发期沿用，交付期换公司企业备案域名** |

**改的原因**（三条，按硬度排）：
1. **数据隔离** —— 学生表含姓名、性别、是否成年、电话，属**未成年人敏感个人信息**（PIPL），不该与个人项目混跑
2. **故障隔离** —— 个人站挂了不该连带公司的考勤系统下线，反之亦然
3. **责任清晰** —— 买断后这是交付物，跑在独立机器上才说得清

**关键发现——「先用个人名义备案，以后再转公司」是条单行道**：

- 绝大多数省份**不支持个人备案 → 企业备案直接变更**，只能注销重备
- 注销重备期间**网站必须停摆**（域名无法访问境内服务器），审核 1~20 工作日
- **小程序被一起锁死**：小程序备案主体须与注册主体一致，主体变更同样要注销重备
- 「域名归我、备案用公司」也走不通——企业备案要求域名实名就是企业

→ **结论：现在什么都别注册**，开发期复用 `jiaowu.palmsugar.cn`（子域名无需单独备案），谈成后由公司注册 + 企业备案，一步到位。

**待确认**：企业备案通常要求备案主体与服务器账号实名主体一致。服务器在用户名下、备案主体是公司，能否用**授权委托书**通过——**买断谈判前问腾讯云备案客服**。

**✅ 切换成本几乎为零**：服务器全程不换，交付时只改一条 DNS 解析，不涉及数据迁移、不停服。这正是「现在就分开服务器」的最大收益。
