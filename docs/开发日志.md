### ★ 关键决策

**1. 1对2 归进「只有出勤才扣」**

用户的原话：

> 对于 1对1 和 1对2 的学生来说，他买多少课时就是多少，所以就是直接按照学生
> 自己的课时来扣就好，上课了就扣课时，没上就不扣。而小班学生的课时是固定的，
> 一个班里的 3-5 个学生，上课都是同步的，上一次课就消一次的课时。除非没有上课，
> 否则其中 1 个学生没有来也不影响扣课时。我的意思就是没有来的也会扣课时。

**他的分界线不是「人数」而是「课时归谁」**：1对1 / 1对2 的课时是**学生自己买的**，
小班的课时是**整班一起走的**。所以我们把判定集抽成了一个有名字的常量，
不再散着写 `'1对1'`：

```python
PER_STUDENT_HOURS_TYPES: frozenset[str] = frozenset({"1对1", "1对2"})
```

⚠️ **上一轮这里只有 1对1，而 1对2 悄悄落到了「小班那一档」** —— 也就是说 1对2
的学生请假会被照扣。改之前 254 个测试全绿但**没有一个覆盖 1对2**，所以这个口子
一直没被测试发现。本轮补了 3 个用例（只扣出勤的 / 全员没来不扣 / 改考勤重算要退），
并用「把常量改回只有 1对1」验证过它们**确实会红**。

**2. 「班级只记上了多少课时」—— 这个提案不用改代码**

用户问的是要不要「取消班级层面的扣课时数据」。查了一遍：**现在就没有**。

- 扣课时只写 `hour_transactions`，每行都挂着一个 `student_id`，**天然是按学生的**
- 班级那边的 `total_hours` 是 `SUM(lessons.hours) WHERE status='completed'`，
  **每次现算**，是个只读的展示值 —— 它不参与任何扣减，删掉它也不影响一分钱
- 所以「两本账」的风险从一开始就不存在，不需要做数据迁移

**3. 分类卡：改成人话，并按类型筛而不是按班名筛**

卡面从 `YDY / YDE / XB` 换成 `1对1 / 1对2 / 小班`。两个细节：

- `key` 和 `label` **故意分开**：`key` 进 URL query，所以必须是 ASCII
  （中文进 query 会变成 `%E5%AF%B9%E4%B8%80` 那种没法看的链接）
- **筛的是 `class_type`，不是班级名前缀**。历史遗留的自定义班名（「沐晨提高班」）
  没有 `YDY` 前缀，按前缀筛会让它们切到「1对1」后凭空消失
- 小班三档（1对3/1对4/1对5）**合成一张卡** —— 对用户来说「小班」就是一档

卡的定义从 `CLASS_NAME_RULES` 推出来（`CLASS_TABS`），以后加个前缀会自动多一张卡，
不用改前端。

> ⚠️ **已知口子**：`class_type` 认不出来的班（`VIP` / 冲刺班型）只出现在「总览」里，
> 没有「其他」这张卡。用户没要求，**没有自作主张加**。

### ★ 关键决策

**1. 扣课时口径改成按班型，推翻了原来的「三种状态都扣」**

用户的原话：

> 1对1的班级，只有出勤才扣课时；其他班级，只要开课就一定扣课时，
> 无论其中个别学生是否出勤。

这**推翻了 Phase 2 验收时定的口径**（当时是「出勤/请假/缺勤都扣，只有取消不扣」）。
新口径落在 `core/class_rules.charges_only_present`，**按 `class_type` 判而不是按
班级名前缀**（前缀只是拿来推导 `class_type` 的）。认不出的自定义类型归到「其他」
那一边 —— **宁可多收，不能漏收**。

「班级和个人的都会扣」这句按「不管哪种班型，该扣的都扣掉」理解，
**没有**引出一个新的「班级课时池」概念 —— 那需要一张新表，不是这句话能推出的事。

> ✅ **这一条用户 2026-10-07 想清楚了，搁置解除。** 他给的口径是：
>
> > 干脆只记录每个学生各自的课时如何？班级只记录上了多少课时，
> > 不做扣课时的数据，不就好了？
>
> 也就是**只有学生一本账，班级那份只是「上了多少课时」的统计**。查下来
> 现在的实现**正好就是这样**（`hour_transactions` 全挂着 `student_id`，
> 班级的 `total_hours` 是 `SUM(lessons.hours)` 现算的只读展示值），
> **零改动**。详见本文件 2026-10-07 那条。~~两本账~~ 这个方向**不做了**。

**2. 课时不足 = 整节课失败，不是扣成负数**

用户选的方案是「整节课失败，列出是谁」。所以 `complete_lesson` 在写任何一行之前
先查该扣的人余额够不够，不够就 400 并列出「谁（剩 X，需要 Y）」。
全有或全无 —— 和其他批量操作一个道理：部分成功会让老师不知道该不该重试，
而重试会重复扣课时。

⚠️ 「余额可以为负」这条**只留给手工 `adjust`**（纠错/退费用），完成上课不在此列。

**3. 考勤一改，课时跟着重算**

1对1 改成「只有出勤才扣」之后，如果事后把出勤改成请假却不退课时，
老师点错一次就会静默多收学生的钱，而且账面看不出来。用户选的是「跟着重算」。

做法是**只动差额**（该扣没扣的补上、不该扣而扣了的删掉），不是「全删了重建」——
重建会把原有流水的 `created_at` 抹掉，审计痕迹就没了。

**4. 上课内容 `content` 和排课备注 `note` 是两列**

排课时的 `note` 是给排课人自己看的（「这节换成王老师」），上完课的 `content` 是
教学记录（「第三章语法复盘」）。**故意不合并** —— 合并的话，完成上课时的写入
会把排课备注吃掉。

**5. 导航栏：合同 tab 只给管理员**

用户拍板「管理员能看到合同的 tab，普通老师看不到比较好」。所以 tab 数量是
**可变的**（老师 4 个、管理员 5 个）。

顺带发现一个连带问题：`AppHeader` 的返回键一级页面要不要显示？结论是**不显示** ——
一级页面没有「上一页」，返回键要么把人送去莫名其妙的地方、要么原地不动，
两种都像坏了。所以加了 `:back="false"`。**表单页（新建/编辑）不放底栏**，
填一半误触就全没了。

### ★ 关键决策

**1. 容量口径不是「1对N → N 人」**

最直觉的写法是 `cap = int(class_type[2])`，得到 1对3 → 3、1对4 → 4。
**错**。用户明确的口径是：

> 1对1，上限 1 人 / 1对2，上限 2 人 / 小班，上限 5 人，**只要没有满 5 人都可以**。

即小班三档（1对3 / 1对4 / 1对5）**共用 5 人上限**，不按档位细分。所以
`CLASS_CAPACITY` 是一张手写的表，不是能算出来的东西 —— 代码里专门写了注释挡住
后来的「优化」。认不出的类型给 `None` = **不限制**，免得把历史自定义类型拦死。

**2. 占名额的人数不能只数「还没有行」的**

第一版 `adding` 写的是「在 `class_students` 里没有行的学生数」。**漏了退班又要回来的**：
退班的行会被清掉 `left_on`，人照样回到在册名单，**他也要占名额**。判据得是
`row is None or row.left_on is not None`。这是写的时候自己发现的，补了一条测试钉住。

**3. 超员的历史数据不写迁移脚本**

dev 库里的 `YDY001N5`（1对1）**真的有 2 个在册学生** —— 规则上线前建的，规则不能追溯。
选择**不动数据库**：`PATCH` 只在类型**真的变了**时才查容量（本来就超员的班改个错别字
不该被拦，否则用户没法自救），入班时拦住，界面上打「超员」标记让用户自己移出。

**4. 分类卡的前缀从后端推导，不在页面里写死**

`stores/meta.js` 的 `classPrefixes` 从 `GET /classes/rules` 的 `class_name_rules` +
`small_prefix` 拼出来。以后后端加个 `YDF`，前端**自动多一张卡**。过滤纯前端做了 ——
班级总数几十个，犯不上多跑一趟接口。

### ★ 那个「一直加载中」的 bug（值得单独记）

`StudentDetailView` 读 `detail.transactions`，但这个字段当时**只挂在
`/students/{id}/hours` 上，没进 `/students/{id}` 的详情**。

于是渲染时 `!detail.transactions.length` 抛 TypeError →
**Vue 丢掉整次更新，DOM 冻死在上一帧**（还停在 `loading = true` 的「加载中…」）→
**接口返回 200，后端日志里什么都没有**。

排查顺序很反直觉：看起来像网络卡住，实际网络 5ms 就回来了（直连 8000 和走 5173
代理都试过），**只有浏览器控制台能看见**。最后是靠截图反推的 —— 标题渲染成
「学生」（`detail?.name || '学生'` 的兜底）、没有「编辑」按钮（`v-if="auth.isAdmin && detail"`），
这两个特征只有 `detail === null` 时才同时成立。

**教训两条**：
- 页面读的每个字段都要对得上后端 schema。改后端字段时先看谁在消费
- 「一直加载中」≠ 卡住。先看控制台

顺手修了同一页面上一句已经过期的话：「考勤功能还没上线，这三个数暂时都是 0」——
考勤上一轮就上线了。

**可选加固（尚未做）**：加一个全局 `app.config.errorHandler`，把这类渲染异常
打到界面上。一个 bug 冻了整页且毫无提示，值得有个兜底。等用户点头再加。

点一次提交 → 学生课时被扣。上一轮里恒为 0 的两个统计字段
（班级的「累计已上课时」、学生详情的出勤统计）**这轮自动有值了，前端一行没改** ——
当初把形状先定死的判断是对的。

224 个测试全绿（上轮 168 + 本轮 56）。

### ★ 四个关键决策

**1. 考勤与「完成上课」合并成一个动作**

实施计划原文把「完成」和「提交考勤」并列成两个平级接口，但 §Phase 2 的验收标准
写的是「提交考勤 → 该课变已完成，学生课时被扣」——**自相矛盾**。

改成 `POST /lessons/{id}/complete` 收可选的 `items`，一个事务里写考勤 + 扣课时 + 改状态，
**以合并为准**。理由：老师的真实动作就是「勾完点提交」，分两步意味着中间那个状态
（课已扣课时但还没点名）既没用又要额外处理。`items` 保持可省（不带 body 默认全出勤），
跟原签名兼容。

`POST /lessons/{id}/attendance` 保留了，但**只管事后改**，且只允许 `completed` 的课。

**2. `BEGIN IMMEDIATE` 刻意不写**

实施计划 §4.1 原本要求手动 `BEGIN IMMEDIATE` 防并发双扣。**做不到**：
`session.get()` 一执行，SQLAlchemy 2.0 的 autobegin 已经开了事务，
此时再 `BEGIN IMMEDIATE` 直接报 `cannot start a transaction within a transaction`。

而它想防的那件事**已经被数据库层兜住了**：第二个并发事务的 `consume` insert 撞
`uq_consume_once` 唯一索引 → `IntegrityError` → rollback（考勤一起回滚）→ 翻译成 409。

所以真正要写的代码是**在 router 里 `except IntegrityError`**，不是手动控事务。
这也印证了「service 层不 commit」这个约定的价值 —— 事务边界留在 router，
一个 try/except 就能兜住整个多步操作。

**3. 课程生命周期冲突统一 409**

完成 / 取消 / 删除 / 改考勤的状态不对，全部 **409 Conflict**。⚠️
**跟班级、学生模块用 400 表示「已经是停用状态」不一样** —— 那两个是「操作重复了」，
课程这几个是「对象状态不允许这个操作」，语义不同。照抄会得到不一致的接口。

**4. `PATCH` / `DELETE` 只允许 `scheduled` 的课**

已完成的课改 `hours` 会让 `lessons.hours` 跟已经写下的 `consume` 流水（`-旧 hours`）对不上，
工资表当场失真。要改就**取消重排**（取消会把课时退回去，重排再扣一次，账是平的）。

同理 `PATCH` **不允许改 `class_id`** —— 换班就是取消重排，避免「改了班，`rate` 快照算谁的」。

### 其他取舍

- **老师权限边界**：排课限管理员；**完成 / 考勤 / 查看只能操作自己的课**
  （`lesson.teacher_id == self`，否则 403）。老师调 `GET /lessons?teacher_id=` **传什么都无效**，
  服务端强制改回自己的 id —— 否则老师能翻遍全校的课
- **取消课程要退回课时**：删掉该课的 `consume` 流水，学生余额自然回升。但 `attendance` 行
  **刻意保留** —— 那是「本来安排了、后来取消了」的痕迹，删了就看不出原本要给谁上
- **`rate` 服务端快照，接口不收这个字段**：让客户端传费率等于谁都能给自己开 999 元/时。
  `LessonCreate` / `LessonUpdate` 里**根本没有 `rate`**，前端也没有费率输入框
- **没有 `stores/lessons.js`**（偏离原计划）：代码库的真实模式是只有跨页面共享的状态才建 store
  （就 `auth` / `meta` 两个），课程页面各拉各的，store 只是个多余的中转层
- **日视图的日期放 `route.query.date`**：不是组件 `ref`。这样「进详情→返回」不丢日期、
  刷新还在当天、链接能直接发人。用 `watch(date, load)` 而不是在每个入口手动调，
  因为**浏览器前进/后退也会改 query**
- **月视图日历本轮没做**：纯 CSS Grid + 原生 Date 手画是块独立的大工作量，
  日视图已经能验证「老师手机上完成一节课」这条主流程

### ★ 踩到的坑：pydantic 注解被字段名遮住

```python
class LessonUpdate(SQLModel):
    date: date | None = None      # ← TypeError: unsupported operand type(s) for |: 'NoneType' and 'NoneType'
```

报错点在**类创建时**，不是实例化时。原因是 pydantic 求值注解时**能看见类命名空间**：
字段名 `date` 的默认值 `None` 把 `date` 这个类型名绑定掉了，于是 `date | None`
被算成 `None | None`。

`LessonCreate.date: date`（无默认值）能跑，因为那个名字从来没被绑定过 —— 所以这个坑
**只在给字段加默认值的那一刻出现**，看起来毫无道理。

**解法**：`from datetime import date as Date`，用 `Date` / `Date | None`。
顺手把模块里三处原有的裸 `date` 注解也改了，保持一致。

### 顺手修掉一个既有缺陷：枚举 CHECK 约束一条都没落库

上一轮记进待办的那个问题，本轮修了。**修法是删库重建** —— SQLite 不能
`ALTER TABLE ADD CONSTRAINT`，而 `init_db()` 只做 `create_all`，已存在的表不会被改。

具体做法是在 `models.py` 加了个 `enum_check(column, enum_cls, name=...)` 助手，
**从 Python 枚举类推导出 IN 列表**，把约束和枚举钉死在一起。两点值得记：

- **用 `.name` 而不是 `.value`**：SQLAlchemy 的 `Enum` 落库写的是成员**名**。
  本项目各枚举恰好 `name == value`，看着等价，但 `.name` 才是对数据库真正成立的推导
- **改 `__table_args__` 时逐个保留原索引**，尤其 `uq_consume_once` ——
  漏掉它等于拆掉防重复扣课时的安全网，而且不会有任何报错。
  `tests/test_enum_checks.py` 里专门有一条把索引的 `WHERE` 字面量和
  `TxnType.consume.name` 绑在一起的回归测试：改枚举成员名而不同步索引，那里会红

⚠️ **教训**：往枚举里加成员后，测试库每次 `drop_all`/`create_all` 所以会绿，
**生产库不会** —— 必须重建生产库，否则新值被 CHECK 挡在门外。

### 八个正确性要点（这些是取舍，不是实现细节）

1. **重新入班必须复用原行**。`ix_cs_pair` 是 `(class_id, student_id)` **全表唯一**，
   退班再入班直接 `INSERT` 会撞唯一索引。正确做法是清掉 `left_on` 并改 `joined_on`。
   这是本轮最容易写错的一处
2. **`GET /students` 防行数放大**。余额先 `GROUP BY` 聚合成子查询再 LEFT JOIN；
   按班级过滤走 `Student.id.in_(子查询)`，**不再 JOIN 一张表** ——
   多一个 JOIN 会让行数相乘，把 `SUM` 放大成错的钱数（学生在 2 个班，10 课时会显示 20）。
   `coalesce` 保证**没有任何流水的学生也显示 0**，而不是整个从列表里消失
3. **班级 DELETE 是真删，学生 DELETE 是软删**。这两个语义不一样（实施计划 §5.3/§5.4），
   真删前要先清 `class_students`，否则撞外键（`db.py` 开了 `foreign_keys=ON`）
4. **本轮绝不产生 `consume` 流水**。手工入口**显式拒绝**：手工流水的 `lesson_id` 是
   `None`，`uq_consume_once` 根本不拦，放进来那道安全网就形同虚设
5. **批量操作全有或全无**。部分成功会让用户不知道该不该重试，而**重试会重复充值**。
   钱的事，宁可全失败
6. **余额允许为负**。`adjust` 就是用来纠错/退费的，负余额是合法账实，只记录不拦截
7. **费率缺省按类型自动填，但绝不静默兜底**。类型不在费率表里又没给 `rate` → 400，
   否则会录进一个错价，**要等发工资才发现**。PATCH 时改类型**不自动改价**
8. **前缀规则在 `core/class_rules.py` 里是「复制」不是 import**。部署时只上传
   `codes/server`，服务器上没有 `codes/desktop`。⚠️ 两边逻辑必须一致，
   判定不一致会让同一节课在桌面版和后端算出不同时薪

### 踩坑记录

1. **`sqlalchemy.select` 和 `sqlmodel.select` 不是一回事**。单列查询用前者返回的是
   `Row` 元组，`(12.0,) == 12` 会失败；`sqlmodel.select` 才会折成标量。
   抄测试助手函数时漏了这行 import，7 个测试红得莫名其妙
2. **取「今天」不能用 `new Date().toISOString().slice(0, 10)`** —— 那是 **UTC** 日期，
   中国 UTC+8 在本地 00:00~08:00 取出来是**昨天**，入班日期整整差一天。
   写了 `utils/date.js` 的 `todayISO()` 走本地年月日
3. **三态字段不能用 `is not None` 判断「用户传了没」**。`is_adult` 的「未填」就是
   `null`，跟「没传这个字段」长得一模一样 —— 用 `if payload.is_adult is not None` 的话，
   一旦设过成年/未成年就**再也改不回「未知」**，而且提交还成功、值没变，是静默失败。
   `phone` 同理（清空手机号变成空操作）。改用 `model_fields_set` 区分，
   `tests/test_students.py` 里加了四条测试，含一条反向的「没传的字段不会被清空」
4. **`ClassDetailRead` 加了 `has_lessons`**：原计划让前端「编辑时给个费率提示」，
   但接口不暴露「排没排过课」这件事就没法做。加了之后顺带解决了另一个问题 ——
   详情页能**提前把删除按钮禁掉并说明原因**，而不是让人点了才吃 400

**只做脚手架 + 登录闭环，不碰课程/考勤。** 那些后端接口还不存在，
要等 Phase 2+3 后端合并做（原因见「一个排期发现」）。

### 技术选型

Vue 3 + Vite + Vue Router + Pinia，**手写 CSS**（不引 UI 组件库，品牌色完全说了算），
**原生 `fetch`**（不引 axios，封装约 60 行），**JavaScript 不用 TypeScript**
（接口契约由后端 Pydantic 保证，读得懂比类型安全重要）。运行依赖只有 3 个。

实测版本比预期新：`vue 3.5.43` / `vue-router 5.3.1` / `pinia 4.0.3` / `vite 8.3.2`。
两个大版本号**都不带破坏性变更**，但各有细节：

- **Vue Router 5** 核心 API 与 v4 完全一致（这个 major 只是把文件式路由并进了核心），
  但 **5.0.3 起弃用了守卫里的 `next()` 回调**，一律用返回值写法
- **Pinia 4** 是纯 ESM，`@vue/devtools-api` 拆成了 peerDependency

### 关键决策

| 决策 | 理由 |
|---|---|
| **前端只写相对的 `/api`，靠代理** | dev 用 Vite 代理转发到本机 8000，生产用 Nginx 反代。**手机访问时不用改后端 CORS**（同源了），一份代码两处跑 |
| **`client.js` 不 `import router`，改用注入的回调** | 否则 `router → store → api → client → router` 循环依赖，还会把 web 独有的路由拖进本该可移植的网络层。改成 client 只认两个回调，在 `main.js` 里接线 |
| **判定「会话失效」= `401 && 本次带了 token`** | ⚠️ 见下方踩坑 1 |
| **token 存 localStorage，user 不持久化** | role 是权限依据，宁可每次启动向后端要一份真实的 |
| **不建 `components/`** | 只有 2 个表单，抽组件是负收益；而且组件越抽象，移植 uniapp 时越要重写 |

### 踩坑记录

1. **⚠️ 登录失败和 token 过期是同一个状态码** —— 后端密码错也回 401
   （不给撞库的人区分「这个号存在」）。如果 client 把「401 → 登出」写成无条件触发，
   **用户输错一次密码就会被踢出登录态**，而且看起来像玄学。判定条件必须是
   「带了 token 还被 401」。这是本轮最容易写错、也最难查的一处
2. **改密接口只回 `{message}`，不回 user** —— 读源码才发现的。前端改完必须
   自己把本地的 `must_change_password` 置回 false，等响应体是等不到的，
   否则路由守卫会一直把你摁在改密页
3. **`init_superadmin.py` 在 Windows 下会「成功了却报错」** —— 最后一行打印
   `⚠️`，GBK 控制台编不出来，抛 `UnicodeEncodeError`。账号**已经建好了**，
   脚本却带着 traceback 退出，看着像失败。已换成纯中文
4. **手机连不上多半是防火墙** —— Vite 默认只绑 localhost，要 `host: true`；
   另外首次启动时弹的「允许 Node.js 访问网络」如果点了取消，之后不再弹窗

### 一个排期发现

**Phase 2 的验收标准依赖 Phase 3 的数据。**
实施计划里 Phase 2 的验收是「提交考勤 → 该课变已完成，**学生课时被扣**」，
但**学生和班级是 Phase 3**。没有班级就没有课，没有学生就没得扣。

所以 **Phase 2 和 Phase 3 的后端必须合并做**，不能按编号顺序走。实施计划已同步修正。

### 一个实测确认的隐患

**设计文档要求的枚举 `CHECK` 约束，实际一条都没建出来。**
SQLAlchemy 2.0 的 `Enum` 默认 `create_constraint=False`，实测 `users.role`、
`lessons.status`、`attendance.status`、`hour_transactions.type` 建出来都是裸 `VARCHAR`。

最要命的是 `hour_transactions.type`：`uq_consume_once` 这个防重复扣课时的部分唯一索引，
条件是 `WHERE type = 'consume'`——**它的正确性完全押在这个字符串字面量上**。
写错大小写索引就静默失效，同一节课扣两次课时。

**建议尽快修**：现在生产库只有超管一个账号，重建表几乎零成本。已记进实施计划待办。

## 2026-10-04 — ⚠️ 更正：关于「改不了角色」的理由（同日）

### 记错的是什么

上面 Phase 1 的决策表里，「改不了角色」原本写的理由是
**「改角色等于把过去的记录算到另一个身份头上」——这句话是错的。**

改角色时 `user.id` **不变**。梁筱的 200 节课 `teacher_id` 还是梁筱，
工资统计一分不差。**她确实教了那些课，这个事实没有被改写。**

那句话实际描述的是另一件事：**把账号交给另一个人**
（梁筱离职、张三用她的号登录）。那才叫篡改历史，和改角色是两码事。

### 为什么不能再照这个理由做决定

用户当时提出「新建一个管理员号，再把老师的数据复制过去」——
这个绕法**恰恰是在改写历史**：

```sql
UPDATE lessons SET teacher_id = 新号 WHERE teacher_id = 旧号
```

- `created_by` 散在多张表里，漏改一个就是孤儿记录
- 一个人从此有两个账号，不知道登哪个
- 旧号留在库里，哪天被别人拿去用，历史**才真的**错位了

**结论：改角色本身是安全的、正常的。** 要这个能力就直接放开（约 10 行：
只有超管能改、不能改自己），**不要去复制数据**。

### 现状

本期**没做**角色修改，是范围控制——当时只有超管一个账号，用不上。

### 部署方案二次变更（同日晚）

用户提出：系统将来要**被公司买断**，服务器和后期运维仍由用户自己承担。据此改了部署方案。

| 项 | 原方案 | **新方案** |
|---|---|---|
| 服务器 | 与刷题背单词站共用现有 4核4G | **独立新服务器，2核2G / 40G / 3~5Mbps** |
| 域名 | `jiaowu.palmsugar.cn` 长期沿用 | **开发期沿用，交付期换公司企业备案域名** |

**改的原因**（三条，按硬度排）：
1. **数据隔离** —— 学生表含姓名、性别、是否成年、电话，属**未成年人敏感个人信息**（PIPL），不该与个人项目混跑
2. **故障隔离** —— 个人站挂了不该连带公司的考勤系统下线，反之亦然
3. **责任清晰** —— 买断后这是交付物，跑在独立机器上才说得清

**关键发现——「先用个人名义备案，以后再转公司」是条单行道**：

- 绝大多数省份**不支持个人备案 → 企业备案直接变更**，只能注销重备
- 注销重备期间**网站必须停摆**（域名无法访问境内服务器），审核 1~20 工作日
- **小程序被一起锁死**：小程序备案主体须与注册主体一致，主体变更同样要注销重备
- 「域名归我、备案用公司」也走不通——企业备案要求域名实名就是企业

→ **结论：现在什么都别注册**，开发期复用 `jiaowu.palmsugar.cn`（子域名无需单独备案），谈成后由公司注册 + 企业备案，一步到位。

**待确认**：企业备案通常要求备案主体与服务器账号实名主体一致。服务器在用户名下、备案主体是公司，能否用**授权委托书**通过——**买断谈判前问腾讯云备案客服**。

**✅ 切换成本几乎为零**：服务器全程不换，交付时只改一条 DNS 解析，不涉及数据迁移、不停服。这正是「现在就分开服务器」的最大收益。
