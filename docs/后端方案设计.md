## 一、项目定位

从「一个人算工资的小工具」升级为「**培训机构的课程管理系统**」：

- **老师**：看课表 → 签到考勤 → 看自己的课时和课时费 → 导出自己的考勤表
- **管理员**：管老师 / 学生 / 班级 / 排课 → 审批变更 → 导出所有人的考勤表
- **超管**：以上全部 + 管理管理员账号

桌面版（现有 v0.3）**逐步退役**，最后只保留「算课时 + 导考勤表」这个功能——详见第九节。

## 二、角色与权限

| 角色 | 权限范围 |
|---|---|
| **超管** | 全部权限 + **添加 / 修改 / 删除管理员账号** |
| **管理员** | 老师全部权限 + 管学生 / 班级 / 排课 + 审批 + 导出所有人的考勤表 + 管老师 |
| **老师** | 看自己课表、考勤签到、看学生 / 班级（**只读**）、看自己的课时费、导出自己的考勤表 |

> **超管的产生**：系统初始化时用脚本直接在服务器上建一个超管账号，之后所有管理员都由超管在界面上开。这样就不用纠结「第一个管理员从哪来」。

**权限设计原则**：老师能看的，管理员都能看；管理员能改的，老师只能看。界面上按角色显示不同按钮，**同一套页面**。

### 审批流（改课程时间）

```
老师发现某节课时间要变
   ↓
提交修改申请（填新时间 + 原因）
   ↓
任一管理员审批 → 通过 / 驳回
   ↓
通过则课程时间生效，留痕
```

**管理员自己改 → 直接生效，不用审批。**

> 你说得很对：这个审批「只是走个流程」，但它的价值是**让管理员知情、能担责任**。所以设计上要**轻**——一个待办列表 + 通过/驳回两个按钮就够了，不要做成复杂的工作流引擎。

### 回答你的 Q1：FastAPI 还是 Django？

先澄清一个关键误解：

> **「以后学生/老师变多，要不要换框架」——这个担心不成立。**

FastAPI 和 Django 处理几千上万用户都没问题，**框架不是瓶颈**。真正决定能扛多少人的是**数据库**（SQLite → PostgreSQL），跟框架无关。所以不存在「人多了得转 Django」这件事。

再说你担心的两点：

**① 前期自己写管理界面，代价大吗？——中等，但比看起来小。**

关键原因：**你本来就要求老师能看学生和班级**（只读）。这些页面**无论如何都要用 uniapp 写一遍**。管理员无非是在同一套页面上多几个「新增 / 编辑 / 删除」按钮——边际成本很小，而且是复制粘贴的活。

**② 后期维护 Django 会不会更麻烦？——会，因为你会得到两套前端。**

选 Django 的话：
- ✅ 白送一个管理后台（`/admin`），录数据不用写界面
- ⚠️ 但那个后台**风格老旧、手机上很难用**，只适合你在电脑上录数据
- ⚠️ 于是你有两套前端、两套登录、两套权限模型，老师那边还是要用 uniapp 再写一遍
- ⚠️ 审批流要同时出现在两边，容易乱

**③ FastAPI 转 Django 麻烦吗？——很麻烦，等于重写。**

但结论是：**你不会因为「人多」需要转**，所以这个担心可以放下。

### ✅ 结论：已确认用 FastAPI

**决策理由**（用户 2026-09-17 确认）：**框架选择跟人数无关**，而 Django 会带来两套系统的运维负担。故选 FastAPI：单前端、单登录、单权限，管理界面复用教师界面加按钮。

> Django 因为会导致两套系统运维麻烦，已被排除。

## 七之二、⚠️ 三种「课时」必须分清

这是整个系统**最容易搞混、最容易对不上账**的地方。系统里有三种完全不同的「课时」：

| # | 概念 | 归属对象 | 计算方式 | 用途 |
|---|---|---|---|---|
| **1** | **教师课时费** | **老师** | 上了多少节课 × 时薪 | 算工资、导考勤表（= 现有桌面版那套） |
| **2** | **班级已上课时** | **班级** | 这个班累计上过多少次课 | 班级管理页展示 |
| **3** | **学生所剩课时** | **每个学生各算各的** | 购买 − 消耗（流水求和） | 学生管理页展示、家长查询 |

### 为什么学生课时必须独立于班级

因为实际情况是：

- 有学生**只买几节课**（不跟班级的完整课时包走）
- 有学生**同时参加两个班级**

所以**学生的课时余额和班级的课时数天生就不一样**。如果把余额挂在班级上，**一定对不上**。

> **✅ 已确认（用户 2026-09-17）：每个学生一条独立的课时余额，按学生单独扣。**

### 扣课时的规则（已确认）

```
一次课正常上了（这节 hours = 2.5）
   → 班级的「已上课时」+2.5
   → 老师的「课时费」+2.5 小时 × 时薪
   → 该班每个学生的「所剩课时」各扣 2.5   ← 每人扣自己的
```

> **⚠️ 口径澄清（2026-09-18 已确认）**：系统里**「课时」就是「小时数」**，不存在两套换算。
> 上面原文写的「各扣 1 次」应理解为「各扣一次**这节课的小时数**」。用户原话：「课时就是小时数哦。不然还得搞两个不同的时间太麻烦了。我们直接按多少小时算。比如一个班级 48 小时，第一天上 2.5h 第二天上 3h，那就扣 5.5h。」
> 实现即 `hour_transactions.amount = -lesson.hours`。

**关键点**：

| 情况 | 扣不扣课时 | 说明 |
|---|---|---|
| 正常上课 | ✅ 扣 | 全班学生都扣 |
| 学生**请假** | ✅ **照样扣** | 你说得明确：「就算一个学生请假，也算课时」 |
| 学生缺勤/旷课 | ✅ **照样扣** | 用户 2026-09-18 确认，同请假逻辑 |
| **课程取消**（这次课不上） | ❌ **不扣** | 唯一的例外 |

> **重要推论**：出勤状态（出勤 / 请假 / 缺勤）**不影响扣课时**，它只是**记录**（谁来了谁没来）。
> 真正决定扣不扣的是**课程本身有没有上**（`lessons.status`）。

**实现方式**：课程标记为「已上课」时，一次性给该班所有学生各写一条 `consume` 流水。课程若取消，则作废这批流水（或直接不生成）。

## 十、部署：服务器与域名

### ⚠️ 已改为独立服务器（2026-09-26 决策变更）

> **原方案是「与刷题站共用现有 4核4G」，已作废。**
> 理由变了：本系统将来要**被公司买断**，服务器和运维由用户继续提供。共用一台机器在**数据隔离、故障隔离、责任划分**三方面都站不住（学生表含未成年人姓名/年龄等**敏感个人信息**）。

**新方案：单独买一台。**

| 项 | 推荐配置 | 说明 |
|---|---|---|
| 配置 | **2核2G** | 稳态内存约 400~500MB，绰绰有余 |
| 硬盘 | **40G SSD 起** | 数据量约 30MB/年，主要为备份和日志留空间 |
| 带宽 | **3~5Mbps** | 2Mbps 够用（需开 nginx gzip） |
| 地域 | 境内，离用户近 | 要备案，必须境内 |
| 镜像 | Ubuntu 22.04 LTS | |
| 账号 | **用户自己的腾讯云账号** | 保持服务器归属清晰 |

**负载实测依据**（20 老师，学生不登录系统）：

```
Ubuntu 系统      150~250 MB
Nginx              ~15 MB
FastAPI+uvicorn   80~150 MB
SQLite            进程内，几乎不计
─────────────────────────────
稳态合计         约 400~500 MB
```

**结论：2核2G 是甜点，别买 1核（没部署余量），也别买 4核（纯浪费）。** 约 35~60 元/月。

### 域名：分两阶段，**现在不要注册个人域名**

```
【开发期】用已有的
jiaowu.palmsugar.cn          ← 已备案的子域名，零成本零等待

【交付期】换成公司的
jiaowu.<公司域名>            ← 公司企业主体备案
```

**⚠️ 为什么不能「先用个人名义备案，以后再转给公司」**：

1. **绝大多数省份不支持「个人备案 → 企业备案」直接变更**（阿里云口径）。只有少数省份允许，且通常要求个人就是该企业**法定代表人**。不允许的只能**注销原备案 → 企业重新备案**
2. **注销重备期间网站必须停摆**——域名无法访问境内服务器，而审核要 **1~20 个工作日**
3. **小程序会被一起锁死**——小程序备案主体必须与小程序注册主体一致，且**主体变更同样不允许直接改**，也要注销重备
4. **「域名归我、备案用公司」也走不通**——企业备案要求域名实名信息就是企业

**所以：开发演示阶段复用 `jiaowu.palmsugar.cn`（子域名无需单独备案），谈成后再由公司注册域名 + 企业主体备案，一步到位。**

**⚠️ 一个待确认点**：企业备案通常要求**备案主体与服务器账号实名主体一致**。若服务器在用户名下、备案主体是公司，需确认能否用**授权委托书**通过。开工前问腾讯云备案客服。

### 切换成本几乎为零

**服务器从头到尾不换，只换域名。** 交付时做的只有「公司域名备案 + 改一条 DNS 解析」，**不涉及数据迁移、不停服**。这正是「现在就分开服务器」的最大收益。

> ⚠️ **备案注意**：ICP 备案是绑定「**域名 + 接入商（服务商）**」的。**换服务器或新增服务器时，需要做「备案接入」变更**，否则域名可能被断。这是很多人踩的坑。

## 十一、关于微信小程序

### 一个微信账号能挂多少个小程序？

| 主体类型 | 可注册数量 |
|---|---|
| **个人** | **5 个** |
| 个体工商户 | 5 个 |
| **企业 / 政府 / 媒体 / 其他组织** | **50 个** |

补充：**一个邮箱只能注册 1 个小程序**；一个手机号最多绑定 5 个；同一主体下的所有小程序（含已注销、封禁的）都计入上限。

### 小程序的两个硬性门槛

1. **必须 ICP 备案** —— 且**备案主体要与小程序认证主体一致**（个人备案不能用于企业类小程序）。备案流程：提交 → 平台初审（1~2 工作日）→ 工信部短信核验 → 通管局审核（**1~20 个工作日**）
2. **必须 HTTPS** —— HTTP 被全面禁用；证书要有效、TLS 1.2+、域名与后台登记完全一致
3. **域名要在微信后台配置**（`request` 合法域名等），还要放校验文件到网站根目录

> ⚠️ 有一类小程序有个限制：**个人主体不能使用 `web-view`**。不过 uniapp 是**编译成原生小程序代码**（不是 web-view 套壳），所以不受影响。

### 你的思路：先网页、后小程序 —— **完全正确** ✅

理由：

1. **网页版能快速验证功能**，改一版几分钟，不用等审核
2. **uniapp 同一套代码**，后面编译成小程序，**前端代码基本复用**
3. **小程序有备案 + 审核周期**，放后面不会卡住前面的进度
4. 前一个项目小程序也没做——**先跑通一个，再复制经验**

**唯一要提前准备的**：如果这个系统最终要上小程序，**备案主体最好和你的小程序主体一致**，别到时候才发现对不上。这个可以现在就想想。
