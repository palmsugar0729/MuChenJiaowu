## 一、目录结构

### 目标形态

```
MuchenCourseManagement/
├── codes/
│   ├── desktop/          ← 现有桌面版（v0.3 冻结，逐步退役）
│   ├── server/           ← 【新】FastAPI 后端
│   └── web/              ← 【新】uniapp 前端
├── docs/
├── notes/
└── assets/
```

### 为什么要把桌面版挪进 `desktop/`

不挪也能跑，但会有三个 `main.py` 混在 `codes/` 根下的问题：桌面版要 PySide6、服务端要 FastAPI，**两个虚拟环境依赖方向相反**，放一层会互相干扰（`import config` 之类的裸导入最容易撞）。

**一次机械迁移，越早越便宜。**

### ⚠️ 迁移桌面版时必须同步改的地方

**这是 Phase 0 里最容易漏的一步**——漏了会导致「打包功能坏掉」，而桌面版是你每月交报表的生产工具。

| 文件 | 改什么 |
|---|---|
| `.github/workflows/build.yml` | 两处 `cd codes` → `cd codes/desktop`；`pip install -r codes/requirements.txt` → `codes/desktop/requirements.txt`；产物路径 `codes/dist/...` → `codes/desktop/dist/...` |
| `.gitignore` | `codes/build/` → `codes/desktop/build/`；`codes/dist/` → `codes/desktop/dist/`；`codes/*.spec` → `codes/desktop/*.spec` |
| `AGENTS.md` | 「代码组织」和「架构分层」两节要重写 |
| `codes/desktop/build.bat` | **不用改**——它用相对路径 `main.py`，在目录内双击照样work |

**安全保证**：
- 用 `git mv` 迁移，**历史完整保留**
- `codes/dist/` 下的历史 exe 是**独立可执行文件**，不依赖源码路径，**移动源码不影响它们运行**
- 迁移后**立刻验证一次**：双击 `build.bat`，确认能重新打出 exe

### 三个子目录的职责

| 目录 | 技术栈 | 独立虚拟环境 |
|---|---|---|
| `codes/desktop/` | Python 3.13 + PySide6 | `codes/desktop/.venv` |
| `codes/server/` | Python 3.11+ + FastAPI | `codes/server/.venv` |
| `codes/web/` | Node 18+ + uniapp (Vue 3) | `npm` 管理 |

> **为什么服务端写 3.11+ 而不是 3.13**：服务器上 Ubuntu 的默认 Python 更适合 3.11/3.12，且 FastAPI 生态在 3.11 上最稳。桌面版继续用 3.13，互不影响。

## 三、数据库设计（完整 DDL）

SQLite，**必须开 WAL 模式**：

```python
# db.py 中，连接建立后执行
PRAGMA journal_mode = WAL;      # 读写并发，避免「database is locked」
PRAGMA foreign_keys = ON;       # SQLite 默认关闭外键，必须手动开
PRAGMA busy_timeout = 5000;
```

> **服务器时区设 `Asia/Shanghai`**（`sudo timedatectl set-timezone Asia/Shanghai`）。
>
> **📌 实现时的两处调整（2026-09-26）**——原设计写的是「全部存 TEXT 本地时间」，实际落地时改了：
>
> | 项 | 原设计 | **实际实现** | 原因 |
> |---|---|---|---|
> | 日期/时间字段 | TEXT 字符串 | SQLAlchemy `Date` / `Time` 类型 | 类型安全，SQLAlchemy 自动处理转换 |
> | 审计时间戳 | TEXT 本地时间 | `UTCDateTime`（**存 UTC**） | SQLModel 0.0.47 只支持这一种带时区的存法；绕过它得 hack 类型系统 |
>
> **为什么存 UTC 无害**：`created_at` / `recorded_at` / `requested_at` **全是审计时间戳**，没有任何业务逻辑依赖它们做跨天判断。真正的业务日期（`lesson_date` / `joined_on`）是**独立的 `Date` 字段，不受影响**。
>
> 用法是 `Field(..., sa_type=UTCDateTime)`，**注解仍写 `datetime`**——`UTCDateTime` 是 SQLAlchemy 类型，直接当注解用 pydantic 会报错。

### 3.1 users — 用户（超管 / 管理员 / 老师）

```sql
CREATE TABLE users (
    id                   INTEGER PRIMARY KEY AUTOINCREMENT,
    phone                TEXT    NOT NULL UNIQUE,      -- 登录标识
    display_name         TEXT    NOT NULL,             -- 真实姓名
    password_hash        TEXT    NOT NULL,             -- bcrypt，绝不存明文
    role                 TEXT    NOT NULL
                         CHECK (role IN ('super_admin', 'admin', 'teacher')),
    is_active            INTEGER NOT NULL DEFAULT 1,   -- 停用而非删除
    must_change_password INTEGER NOT NULL DEFAULT 1,   -- 首次登录强制改密
    created_at           TEXT    NOT NULL DEFAULT (datetime('now', 'localtime')),
    updated_at           TEXT
);
CREATE INDEX idx_users_role ON users(role);
```

> **学生不在这张表里**。学生不是用户，是数据记录——他们永远不登录。

### 3.2 classes — 班级

```sql
CREATE TABLE classes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL UNIQUE,        -- 班级名（如「沐晨提高班」）
    class_type TEXT    NOT NULL,               -- 1对1 / 1对2 …（决定时薪档位）
    rate       REAL    NOT NULL,               -- 当前时薪（元/时）
    note       TEXT    NOT NULL DEFAULT '',
    is_active  INTEGER NOT NULL DEFAULT 1,
    created_at TEXT    NOT NULL DEFAULT (datetime('now', 'localtime'))
);
```

**设计取舍**：方案文档里列了独立的 `rates` 表，这里**合并进 `classes`**。理由：费率就是班级的一个属性，没有跨班级复用的场景，单独建表只会多一次 JOIN。费率档位（1对1=80 等）通过 `class_type` 区分。

### 3.3 students — 学生

```sql
CREATE TABLE students (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT    NOT NULL,
    gender     TEXT    CHECK (gender IN ('男', '女', '')),
    is_adult   INTEGER,                        -- 1=成年 0=未成年 NULL=未知
    phone      TEXT,                           -- 联系电话（可选）
    note       TEXT    NOT NULL DEFAULT '',
    is_active  INTEGER NOT NULL DEFAULT 1,
    created_at TEXT    NOT NULL DEFAULT (datetime('now', 'localtime'))
);
CREATE INDEX idx_students_active ON students(is_active);
```

> ⚠️ **这里没有 `remaining_hours` 字段**。余额一律由流水求和算出——涉及钱，必须能追溯每一笔。见 3.6。

### 3.4 class_students — 班级-学生（多对多）

```sql
CREATE TABLE class_students (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    class_id   INTEGER NOT NULL REFERENCES classes(id),
    student_id INTEGER NOT NULL REFERENCES students(id),
    joined_on  TEXT    NOT NULL,               -- 加入日期
    left_on    TEXT,                           -- 退出日期，NULL=在册
    UNIQUE (class_id, student_id)
);
CREATE INDEX idx_cs_class   ON class_students(class_id);
CREATE INDEX idx_cs_student ON class_students(student_id);
```

> **学生可以同时在多个班**（方案里明确的情况），所以是多对多。
>
> `joined_on` 的用处：学生中途加入时，**之前已上完的课不会补扣**——因为流水是在「完成课程」那一刻写给「当时在册的学生」的，天然就对了。

### 3.5 lessons — 课程（排课）

```sql
CREATE TABLE lessons (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    class_id   INTEGER NOT NULL REFERENCES classes(id),
    teacher_id INTEGER NOT NULL REFERENCES users(id),
    lesson_date TEXT   NOT NULL,               -- YYYY-MM-DD
    start_time  TEXT   NOT NULL,               -- HH:MM
    hours       REAL   NOT NULL DEFAULT 1.0,   -- 课时数（支持 1.5 这种）
    rate        REAL   NOT NULL,               -- ★ 时薪快照，见下方说明
    status     TEXT    NOT NULL DEFAULT 'scheduled'
               CHECK (status IN ('scheduled', 'completed', 'cancelled')),
    note       TEXT    NOT NULL DEFAULT '',
    created_by INTEGER REFERENCES users(id),
    created_at TEXT    NOT NULL DEFAULT (datetime('now', 'localtime')),
    updated_at TEXT
);
CREATE INDEX idx_lessons_date          ON lessons(lesson_date);
CREATE INDEX idx_lessons_teacher_date  ON lessons(teacher_id, lesson_date);
CREATE INDEX idx_lessons_class         ON lessons(class_id);
```

> **★ 为什么 `rate` 要快照**：班级费率将来可能调整。如果历史课程实时 JOIN `classes.rate` 算工资，**改一次费率会篡改过去所有月份的工资表**——交出去的报表就对不上了。所以排课时把当时费率抄一份到 `lessons.rate`，历史永久冻结。
>
> `status` 只有三个值。**改期不改 status**，改期痕迹留在 `approvals` 表里。

### 3.6 hour_transactions — 学生课时流水 ★

**全系统最关键的一张表。**

```sql
CREATE TABLE hour_transactions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    student_id INTEGER NOT NULL REFERENCES students(id),
    type       TEXT    NOT NULL
               CHECK (type IN ('purchase', 'consume', 'adjust')),
    amount     REAL    NOT NULL,               -- 购买/调整为正，消耗为负
    lesson_id  INTEGER REFERENCES lessons(id), -- 因哪节课消耗（购买时 NULL）
    note       TEXT    NOT NULL DEFAULT '',
    created_by INTEGER REFERENCES users(id),
    created_at TEXT    NOT NULL DEFAULT (datetime('now', 'localtime'))
);

-- ★★ 防重复扣课时：同一节课对同一学生，只允许一条消耗流水
CREATE UNIQUE INDEX uq_consume_once
    ON hour_transactions(lesson_id, student_id)
    WHERE type = 'consume';

CREATE INDEX idx_ht_student ON hour_transactions(student_id);
```

**学生所剩课时 = 该学生所有流水求和**，不存冗余字段：

```sql
SELECT COALESCE(SUM(amount), 0) FROM hour_transactions WHERE student_id = ?;
```

> **`uq_consume_once` 这个部分唯一索引是防重复扣的安全网**。老师误点两次「完成上课」、或者网络重试导致请求重发，都不会把学生课时扣两遍——第二次写入直接被数据库拒绝。

### 3.7 attendance — 出勤记录

```sql
CREATE TABLE attendance (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    lesson_id   INTEGER NOT NULL REFERENCES lessons(id) ON DELETE CASCADE,
    student_id  INTEGER NOT NULL REFERENCES students(id),
    status      TEXT    NOT NULL
                CHECK (status IN ('present', 'leave', 'absent')),  -- 出勤/请假/缺勤
    recorded_by INTEGER REFERENCES users(id),
    recorded_at TEXT,
    UNIQUE (lesson_id, student_id)
);
```

> ⚠️ **出勤状态不影响扣课时**。出勤 / 请假 / 缺勤**三种都照样扣**（用户 2026-09-18 确认缺勤也扣）。这张表**只是记录**「谁来了谁没来」，用来给家长看。
>
> 真正决定扣不扣的是 `lessons.status`——**只有课程取消才不扣**。

### 3.8 approvals — 审批

```sql
CREATE TABLE approvals (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    type          TEXT    NOT NULL,            -- 目前只有 lesson_reschedule
    target_id     INTEGER NOT NULL,            -- lessons.id
    payload       TEXT    NOT NULL,            -- JSON：新日期/时间/原因
    status        TEXT    NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending', 'approved', 'rejected', 'withdrawn')),
    requested_by  INTEGER NOT NULL REFERENCES users(id),
    requested_at  TEXT    NOT NULL,
    reviewed_by   INTEGER REFERENCES users(id),
    reviewed_at   TEXT,
    reject_reason TEXT
);
CREATE INDEX idx_approvals_status ON approvals(status);
```

> 审批设计**刻意保持轻**——一个待办列表 + 通过/驳回两个按钮。不做工作流引擎、不做多级审批。它的价值是**让管理员知情、能担责任**，不是真的要卡流程。

### 3.9 表关系图

```
users ──┬── lessons.teacher_id
        ├── approvals.requested_by / reviewed_by
        └── hour_transactions.created_by

classes ──┬── lessons.class_id
          └── class_students.class_id ──┐
                                        ├── students
                        class_students.student_id ──┘
                                        │
students ──┬── attendance.student_id ───┘
           └── hour_transactions.student_id

lessons ──┬── attendance.lesson_id
          └── hour_transactions.lesson_id  ← 消耗流水指回课程
```

## 四、核心业务逻辑

### 4.1 ★ 完成课程（扣课时的唯一入口）

`POST /api/lessons/{id}/complete` —— **整个系统钱算得对不对，全看这个事务**。

```
事务开始（BEGIN IMMEDIATE）
  │
  ├─ 1. 校验：lesson.status 必须是 'scheduled'
  │     否则 409 Conflict（已完成的课不能重复完成）
  │
  ├─ 2. 查该班当时在册的学生：
  │     SELECT student_id FROM class_students
  │     WHERE class_id = ?
  │       AND joined_on <= lesson.lesson_date
  │       AND (left_on IS NULL OR left_on > lesson.lesson_date)
  │
  ├─ 3. 给每个学生写一条出勤记录，默认「出勤」
  │     INSERT OR IGNORE INTO attendance (lesson_id, student_id, status)
  │     VALUES (?, ?, 'present')
  │     （老师之后在详情页改成实际的 请假/缺勤）
  │
  ├─ 4. ★ 给每个学生写一条消耗流水：
  │     INSERT OR IGNORE INTO hour_transactions
  │       (student_id, type, amount, lesson_id, created_by)
  │     VALUES (?, 'consume', -lesson.hours, ?, ?)
  │     ↑ amount 为负；hours 默认 1.0，1.5 课时的课就扣 1.5
  │
  └─ 5. UPDATE lessons SET status = 'completed', updated_at = ... WHERE id = ?

事务提交
```

**三条并发/幂等保障**：

| 保障 | 机制 |
|---|---|
| 重复点「完成」 | 第 1 步状态校验 → 409 |
| 请求重发/网络重试 | `uq_consume_once` 唯一索引 → 第二条被数据库拒绝 |
| 两个管理员同时点 | `BEGIN IMMEDIATE` 排他锁 + 状态校验 |

> **✅ 扣多少已确认（2026-09-18）**：`amount = -lesson.hours`，即**按小时数扣**。
> 「课时就是小时数」——2.5 小时的课扣 2.5，与学生买的小时数、老师的计薪口径完全一致，不存在两套换算。详见第十节第 1 条。

### 4.2 取消课程（唯一不扣课时的情况）

`POST /api/lessons/{id}/cancel`：

```
事务开始
  ├─ 1. 校验 status 不为 'cancelled'
  ├─ 2. DELETE FROM hour_transactions WHERE lesson_id = ? AND type = 'consume'
  │     （如果课已经完成过，把扣掉的还回去）
  ├─ 3. UPDATE lessons SET status = 'cancelled'
事务提交
```

> **注意**：如果课**已经完成**了才取消（事后发现不该上），必须**删掉已生成的消耗流水**，学生课时原样退回。已填的出勤记录保留（作为「本来安排了但取消了」的痕迹）。

### 4.3 学生课时余额

```python
def get_balance(db, student_id: int) -> float:
    return db.exec(
        select(func.coalesce(func.sum(HourTransaction.amount), 0.0))
        .where(HourTransaction.student_id == student_id)
    ).one()
```

列表页要显示余额时，**用一条聚合查询批量算**，不要在循环里逐个查（N+1）：

```sql
SELECT s.*, COALESCE(SUM(ht.amount), 0) AS remaining_hours
FROM students s
LEFT JOIN hour_transactions ht ON ht.student_id = s.id
WHERE s.is_active = 1
GROUP BY s.id;
```

### 4.4 购买 / 调整课时

- `purchase`：管理员给学生买课时，`amount` 为正
- `adjust`：手动修正（录错、赠送、退费），可正可负，**必须填备注**
- 两者**都要留 `created_by`**，家长问起来能查到是谁操作的

### 4.5 改期审批

```
老师：POST /api/lessons/{id}/reschedule
        body: { date, start_time, reason }
        → 写入 approvals（status='pending'），课程时间暂不变动

管理员：GET  /api/approvals?status=pending   → 待办列表
        POST /api/approvals/{id}/approve     → 改 lessons 日期/时间，留痕
        POST /api/approvals/{id}/reject      → 填原因，留痕

管理员自己改：PATCH /api/lessons/{id}  → 直接生效，不写 approvals
```

### 4.6 教师课时费统计

```sql
SELECT COALESCE(SUM(hours), 0)                AS total_hours,
       COALESCE(SUM(hours * rate), 0)         AS total_salary
FROM lessons
WHERE teacher_id = ?
  AND status = 'completed'                     -- ★ 只算已完成的课
  AND lesson_date BETWEEN ? AND ?;             -- 月初 / 月末
```

> 用 `rate`（快照）而不是 JOIN 班级当前费率——见 3.5 的说明。

## 五、接口清单

统一前缀 `/api`。除登录外**全部需要 `Authorization: Bearer <token>`**。
响应统一包一层：`{ "data": ..., "message": "..." }`，错误返回 `{ "detail": "..." }` + 对应 HTTP 状态码。

### 5.1 认证与个人信息

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/auth/login` | 公开 | `{phone, password}` → `{access_token, user}` |
| POST | `/auth/change-password` | 登录 | `{old_password, new_password}` |
| GET | `/users/me` | 登录 | 当前用户信息 |
| PATCH | `/users/me` | 登录 | 改自己的 `display_name` / `phone` |

> 登录响应里带 `must_change_password`，前端据此**强制跳转改密页**。

### 5.2 账号管理

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/admin/users?role=&is_active=` | admin | 列表（老师看不了） |
| POST | `/admin/users` | admin | `{phone, display_name, role}` → **返回生成的初始密码** |
| PATCH | `/admin/users/{id}` | admin | 改姓名/手机号/启用停用 |

## 六、Excel 导出复用方案 ★

**好消息**：现有的 `codes/desktop/excel_exporter.py` **完全不依赖 PySide6**，只 import `openpyxl` + `config` + `models`，可以整体搬到服务端。

### 需要改造的两处

**① 解掉对静态费率表的依赖**

现有代码：

```python
class Record:
    @property
    def rate(self) -> float:
        return CLASS_RATES.get(self.class_type, DEFAULT_RATE)   # ← 静态表
```

服务端费率来自 `lessons.rate`（快照），**不是静态表**。改成把 `rate` 作为字段直接传进来：

```python
@dataclass
class ExportRow:
    date: date
    start_time: time
    hours: float
    rate: float          # ← 直接给，不再查表
    class_type: str
    class_name: str
    note: str = ""
```

**② 数据来源从 JSON 换成数据库查询**

```sql
SELECT l.lesson_date, l.start_time, l.hours, l.rate,
       c.class_type, c.name AS class_name, l.note
FROM lessons l
JOIN classes c ON c.id = l.class_id
WHERE l.teacher_id = ?
  AND l.status = 'completed'
  AND l.lesson_date BETWEEN ? AND ?
ORDER BY l.lesson_date, l.start_time;
```

### 必须保持逐字节一致的部分

这张表是**交给领导的**，格式一个字都不能变：

- [x] A~J 共 10 列，列宽 `[13, 8, 10, 10, 14, 10, 14, 14, 10, 12]`
- [x] 第 1 行标题「工资结算表」合并 A1:J1，16 号加粗
- [x] 第 2 行 G 列「姓名：」+ H 列教师名
- [x] 第 3 行表头，浅蓝底 `FFBDD7EE` 加粗
- [x] 第 4 行起数据，F 列**用 Excel 公式** `=D{r}*E{r}` 而非硬编码数值
- [x] 末行合计：G 列 `=SUM(D4:Dn)`、H 列 `=SUM(F4:Fn)`
- [x] 按班级名着色，同班同色（12 色调色板 `COLOR_PALETTE`）
- [x] 导出范围跟随选定的月份

> **验收方法**：拿同一个月的真实数据，**桌面版导出一份、服务端导出一份，逐单元格比对**。这是 Phase 4 的硬性验收标准。

### ✅ 多人导出已确认（2026-09-18）：方案 A

老师的单人导出沿用现有单表格式。**管理员导出所有人** = 一个 xlsx 文件，**每个老师一个 sheet**，sheet 名 = 教师姓名。

> 备选方案 B（合并单 sheet + 姓名列）**暂不做**。若上线前给老板演示时她要求「每个人一个」，那正是方案 A 已经实现的形态；若要求合并，再改也不迟。

## 十、细化决策 —— 已全部确认 ✅（2026-09-18）

| # | 事项 | 结论 |
|---|---|---|
| 1 | **一次课扣多少课时** | ✅ **按小时数扣**，即 `-lesson.hours` |
| 2 | **管理员导出所有人考勤表的形态** | ✅ **一个 xlsx、每人一个 sheet**（方案 A） |
| 3 | **Excel「班级」列导出什么** | ✅ **沿用桌面版，导出班级类型**（1对1 / 1对2 …），**不导出班级名** |

### 第 1 条：课时 = 小时数（用户原话）

> 「课时就是小时数哦。不然还得搞两个不同的时间太麻烦了。我们直接按多少小时算。比如一个班级 48 小时，第一天上 2.5h 第二天上 3h，那就扣 5.5h。」

**系统里只有一个时间口径：`hours`（小时数）。** 不存在「课时」和「小时」两套换算——这消除了整个项目里最容易出错的一个歧义点。

| 场景 | 扣多少 |
|---|---|
| 上一节 2.5 小时的课 | 扣 **2.5** |
| 上一节 3 小时的课 | 扣 **3** |
| 两天分别上 2.5h / 3h | 累计扣 **5.5**，学生原 48h → 剩 **42.5h** |
| 老师课时费 | 同样按 `hours × rate`，与上面同一口径 |

**实现**：见 4.1，`hour_transactions.amount = -lesson.hours`。

### 第 2 条：多人导出的备选

方案 B（合并单 sheet + 姓名列）**暂时不做**。用户备注：上线前给老板演示时若她要求「每个人一个」再调整——留个口子即可，不影响现在的实现。

### 第 3 条：Excel 班级列

桌面版 `excel_exporter.py` 的 I 列写的是 `rec.class_type`（班级类型），**保持原样不动**。表头文字仍是「班级」（不会导出班级名）。

> 即：**交付给领导的表格内容与桌面版完全一致，零差异。** 这也让 Phase 4 的「逐单元格比对」验收标准变得干净——两边应完全一致。
